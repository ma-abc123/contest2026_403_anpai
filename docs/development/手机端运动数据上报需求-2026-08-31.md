# 手机端需求：运动数据上报与疑似跌倒接收（2026-08-31）

> 面向手机端 App（Android）的增量需求。**本档不涉及 AI 语音闭环**——那部分见《手机端AI闭环需求-2026-08-30.md》，已实现。
>
> 手表固件版本：4.8.0（M4 运动与跌倒检测）。本档所有协议字段均为**小端（LE）**，帧格式沿用现有 DataUpload 通道。

---

## 0. 背景

手表新增常驻运动服务（板载 LSM6DS3TR-C），后台持续采样，与 UI 无关。手表会通过 **DataUpload 特征（f3，UUID `12345678-9abc-def0-1234-56789abcdef3`）** 主动上报 4 类新数据：

| sensor_type | 名称 | 触发时机 |
|---|---|---|
| `0x05` | STEPS 今日步数 | 连接建立后立即一条；之后步数变化时，**≥5 秒间隔** |
| `0x06` | ACTIVITY 活动状态 | 分类变化时，**≥5 秒间隔**（带防抖，不会抖动） |
| `0x11` | FALL_EVENT 疑似跌倒 | 事件驱动，低频 |
| `0x12` | MOTION_DATA 原始采集流 | **仅当用户在手表 Exercise 页点 Record 时**，采样流转发 |

已有的 `0x01` 温度 / `0x02` 湿度不受影响，继续按原频率上报。

## 1. 帧格式（f3 DataUpload，Notify 或 Indicate）

```
[version=1(1)] [sensor_type(1)] [payload(N...)]
```

订阅方式不变：写 f3 的 CCC。**建议 `0x0001`（Notify）**；写 `0x0002`（Indicate）手表也兼容（4.7.4 起），但 Indicate 有 ACK 开销，高频 MOTION_DATA 下丢帧率会升高，Notify 优先。

### 1.1 STEPS（0x05）— payload 4 字节

```
steps : uint32 LE   今日步数（手表重启后清零，目前不持久化）
```

### 1.2 ACTIVITY（0x06）— payload 1 字节

```
activity : uint8   0=静止 Rest  1=步行 Walking  2=跑步 Running
```

### 1.3 FALL_EVENT（0x11）— payload 8 字节

```
event     : uint8   1=疑似跌倒确认（倒计时结束无人取消）
                    2=跌倒告警已取消（用户在倒计时内取消了）
                    3=测试事件（手表端 Test 按钮触发的全流程演练）
impact_mg : uint16  冲击峰值 |a|，单位 mg（例如 3200 = 3.2g）
angle_deg : uint8   重力方向变化角估计（0-255 度）
reserved  : uint8×4 保留，置 0，忽略即可
```

**手机端建议行为**：
- `event=1`（疑似跌倒）：高优先级——系统通知（闹钟级）+ 铃声/振动 + 置顶页面，展示 impact/angle 与时间；提供"我没事/拨打紧急联系人"按钮（拨打功能本期可只做 UI 占位）。
- `event=2`（已取消）：普通通知，说明"跌倒告警已取消"。
- `event=3`（测试）：普通通知，用于联调验证，不触发铃声。
- 文案统一用"**疑似跌倒**"，不得表述为医疗级判断。

### 1.4 MOTION_DATA（0x12）— payload 14 字节（原始采集流）

```
t_ms : uint32   相对 Record 开始的毫秒数
x    : int16    加速度 X，mg
y    : int16    加速度 Y，mg
z    : int16    加速度 Z，mg
gx   : int16    陀螺仪 X，mdps
gy   : int16    陀螺仪 Y，mdps
gz   : int16    陀螺仪 Z，mdps
```

说明：
- 这是**抽样视图**：手表采样约 30ms/条（≈33Hz），BLE 信道**每 4 条转发 1 条（≈8Hz）**；完整速率数据走串口日志（`REC,t,x,y,z,gx,gy,gz` 行）。固件常量 `BLE_REC_DEC` 可调到 1（全量转发，超载时手表会自动丢帧，不阻塞）。
- 手机端本期**只需把 0x12 帧原样存档**（JSON 行文件即可），供电脑端离线阈值分析；不需要实时绘图（想做实时曲线更好）。
- Record 结束无显式结束帧；以手机端收到用户操作/断连为准。可以在存档文件头部记录开始时间。

## 2. 频控与丢帧语义

- STEPS/ACTIVITY 的 5 秒频控是手表侧行为，手机端无需去重，但**跌倒事件不做频控、不允许丢**：FALL_EVENT 一定要入库并弹通知。
- 底层若为 Indicate 模式，手表在前一条未被确认时会丢弃新样本（返回 -EAGAIN），这是设计行为；手机端确认要及时。
- MTU 建议 ≥247（跌倒事件仅 10 字节帧头+负载，MTU 23 也能发，但建议统一大 MTU）。

## 3. 验收清单（手机端）

1. 连接手表后 3 秒内收到一条 STEPS（值可与 0 相等）。
2. 佩戴步行 30 秒，ACTIVITY 变为 1；静止 1 分钟后回到 0。
3. 手表 Exercise 页点 **Test**：15 秒倒计时内不取消 → 手机收到 `event=3`（若在真实跌倒状态收到 `event=1`，逻辑分支一致）；倒计时内按 CANCEL 或 KEY2 → `event=3` 分支为取消语义（若为真实事件则 `event=2`）。
4. Record 打开后，手机能以约 8Hz 收到 0x12 帧；连续 5 分钟不崩、不断连。
5. 断开重连后，STEPS 重新上报（值累计），无内存泄漏/崩溃。
6. 全程手表 UI 无卡顿（运动服务在手表侧独立线程，与 UI 隔离）。

## 4. 本期不做

- 跌倒事件的短信/电话外呼（只做通知与 UI）。
- 步数的持久化/历史曲线（手表重启清零；手机端如需曲线可自行积累）。
- 抬腕亮屏、计步算法的自定义配置下发。
- 手表→手机的实时原始流常开（仅 Record 模式）。
