# BLE 故障修复与实机验证交接（2026-10-24）

## 结论

板端当前烧录的是 AI Watch 4.8.10。用户反馈该版本连续 3 次连接成功，连接速度较快。我在串口采集期间还观察到一次约 194 秒的连接会话，手机完成时间同步并下发多条 GATT 命令，结束采集前没有 Hardware Error 或断连记录。

4.8.10 包含 HCPU/LCPU 启动期 IPC ring 初始化调整、HCI 错误自愈，以及本次新增的失联控制器强制 host teardown。4.8.10 的正常连接已在实机验证；强制 teardown 新分支尚未在 4.8.10 上由一次新的控制器故障触发，因此它目前只有编译验证，不能声称已实机验证其恢复结果。

## 故障与现场证据

2026-10-24 的原始问题有两种表现：bring-up 时 HCI 命令随机超时、控制器不再应答；或广播后手机连接，LCPU 随即上报 `Hardware error, hardware code: 0`。已观测到的 bring-up 死点分布在多个早期及广播配置 opcode，不能据此认定问题只在广播命令。

4.8.9 上的一次现场记录为：手机连接后约 331 ms 收到 Hardware Error，串口打印恢复起始、LCPU evidence 和断连回调；随后没有 teardown 完成或重新广播日志。恢复函数紧接着调用 `bt_disable_mc()`，现场表现为调用后无继续输出，但具体卡在该函数内部哪一步尚未被栈回溯确认。

补丁 blob 比对结果已确认：G1 与 baseline 中的 legacy `patch_bin`、`lcpu_bin`、`patch_list` 三段内容及 SHA-256 一致，仅镜像地址不同。因此本次修复没有改动闭源 LCPU 固件，也没有证据证明 G1 裁剪是随机 LCPU Hardware Error 的原因。

## 代码改动

### 4.8.9 中已有的 IPC 与故障自愈改动

- 在 [sf32lb52_lcpu_boot.c](/home/ma/openvela-contest403/vendor/sifli/chips/sf32lb52/sf32lb52_lcpu_boot.c) 的 LCPU release 前调用 `sf32lb52_bt_prepare_lcpu_boot()`：失效化旧 L2H ring header、清 mailbox pending、打开 IPC queue 并清理 H2L TX ring。这样 HCPU 不会等 LCPU 已运行后才初始化 H2L queue。
- 在 [sf32lb52_bt_adapter.c](/home/ma/openvela-contest403/vendor/sifli/chips/sf32lb52/sf32lb52_bt_adapter.c) 中把 RX ring 消费延后到 ring header 通过校验、HCPU read index 与 LCPU write index 同步、D-cache 清理完成之后；用 `rx_enabled` 阻止队列初始化期间的通知进入 host。ring 未就绪时会关闭 queue、停止 LCPU 并清理状态。
- 在 [hci_core.c](/home/ma/openvela-contest403/external/zblue/zblue/subsys/bluetooth/host/hci_core.c) 中，HCI 同步命令超时会回调故障通知；bridge 记录 Hardware Error 或超时 opcode，应用主循环再执行恢复，避免在 HCI RX/命令回调上下文中做阻塞 teardown。
- bridge recovery 会记录故障类型、opcode 和 LCPU evidence；连接回调增加连接时长日志，便于判断连接后崩溃的时间点。

### 4.8.10 本次新增的 teardown 修复

- 在 [bluetooth.h](/home/ma/openvela-contest403/external/zblue/zblue/include/zephyr/bluetooth/bluetooth.h) 和 [hci_core.c](/home/ma/openvela-contest403/external/zblue/zblue/subsys/bluetooth/host/hci_core.c) 增加 `bt_disable_force_mc()`。普通 `bt_disable_mc()` 行为不变；force 入口跳过向失联控制器发送 `HCI_Reset`，继续释放 host 状态并关闭 HCI driver。
- [sf32lb52_ble_bridge.c](/home/ma/openvela-contest403/vendor/sifli/chips/sf32lb52/sf32lb52_ble_bridge.c) 在已收到 Hardware Error 或 HCI 命令超时后使用 force 入口，并打印 teardown 开始和返回结果，再重建 Bluetooth host 和广播。
- driver close 会走适配层 deinit/halt LCPU。这里的 `lcpu_power_off()` 使用 HAL reset-and-halt 路径，不是切断 LCPU 电源域。
- [ai_watch_main.c](/home/ma/openvela-contest403/contest2026_403_anpai/app/ai_watch/ai_watch_main.c) 版本号更新为 `4.8.10`。

## 实机验证

- 4.8.10 首次启动完成，串口出现版本号、LCPU ring ready、HCI 5.3、`advertising as "AI-Watch-403"` 和 GATT ready。
- 用户反馈：4.8.10 连续 3 次连接成功，速度较快。
- 本次串口会话：手机连接成功；Status/Data CCC 均设为 `0x0002`；Timesync 写入被接受并应用；手机侧 AI trigger、文本和提醒命令进入手表应用。连接后约 194 秒的日志窗口内没有 Hardware Error 或断连记录。
- 4.8.10 这次连接没有触发控制器故障，故 `bt_disable_force_mc()` 的硬件故障恢复分支未执行。需要将来有自然复现时检查日志是否依次出现 `force host teardown begin`、`force host teardown result=0`、新一轮 HCI 初始化和 `ready`；本次不继续做长期稳定性测试。

## 范围与未决项

- 这些结果表明 4.8.10 在当前几次连接中工作正常；样本数不足以证明 LCPU 随机 Hardware Error 已根治，也不足以确认 G1 与故障有因果关系。
- 傍晚出现过 SFBL/ADC/flash 阶段、早于 NuttX 和 BLE 初始化的启动循环。4.8.10 本次启动成功，但 BLE/IPC 修改不针对该 pre-kernel 启动问题，不能据此认定它已修复。
