没有把旧交接文档的推测当作结论。参赛仓基线 HEAD `3ad645d`，
vendor/sifli HEAD `cccbff8`。

基线镜像：`~/huangshan-logs/bin_4873_before_ringfix_20261103.bin`，SHA256：

本轮原始日志 `~/huangshan-logs/ble_current_probe_20261103.log` 与主机阶段

## 根因机制与源码证据

`vendor/sifli/chips/sf32lb52/ipc_queue/common/circular_buf.h` 的环头是
20 字节，`read_idx_mirror` 位于 +8，`write_idx_mirror` 位于 +12。
两核各自拥有的索引和前 12 字节数据位于同一条 32 字节 DCache 行。

旧适配器 RX：invalidate → 读取 LCPU 的写指针并复制数据 → 更新 HCPU
读指针 → clean 环头。若 LCPU 在此期间写了下一批数据，clean 会连同
旧写指针、旧数据一起回写，覆盖对端新状态。HCPU 关中断挡不住 LCPU。
TX 方向也存在同一问题，而且会先单独发布一个 H4 类型字节，再发布
opcode/参数；覆盖对端读指针可能造成重复读或字节错位。

厂商 SDK 的 `Templates/system_bf0_ap.c::mpu_config()` 明确把 HCPU SRAM
和 LCPU SRAM 配为 `ATTR_RAM=0x44`（Normal Non-cacheable）。当前 NuttX
自定义 `__start()` 没有调用该配置，却开启 DCache，因此原生 IPC 所依赖
的共享内存属性丢失。显式 clean/invalidate 不能修复同一缓存行双核
写入的所有权冲突。

历史 `connect_4873_harness_20261103d.log` 中还出现发送 `0x2009` 后收到
`CS opcode=0x0901` 的异常，与字节错位相容；本轮没有 HCI 原始逐字节
总线取证，因此不把该单条日志视为缓存覆盖的直接观测。

## 修复

- `vendor/sifli/chips/sf32lb52/sifli_start.c`：在开启缓存及初始化 IPC 前，
  使用 ARMv8-M MPU 将 TX `0x2007FE00–0x2007FFFF`、RX
  `0x20405C00–0x20405DFF` 两块各 512 字节区域设为共享、Normal NC、
  可读写、不可执行。其余特权地址保留默认内存映射和缓存。
- 清理继承的 MPU 区域，防止 ARMv8-M 重叠映射；当前是 flat 且
  `CONFIG_ARM_MPU` 关闭。未来开启 NuttX MPU 时必须把共享区放入统一
  MPU 表，源码以编译错误阻止静默丢失此约束。
- `sf32lb52_bt_adapter.c`：打印实际 MPU CTRL、MAIR 和环地址。
  验证值是 `ctrl=00000005 attr=44 tx=2007fe00 rx=20405c00`。
- 未改 LCPU blob、传感器、显示缓冲布局、连接静默与恢复退避。
- 版本 `4.8.80-blecache-panel`，通过现有 `tools/build_panel.sh` 构建。

镜像：`~/huangshan-logs/bin_4880_blecache_panel.bin`，SHA256：
`f0a55d829f57f0a55310fa2cce9da828129dbb96499a31b1c801cdfd56dfde5c`。
构建成功，烧录 exit=0 且最终 100%；两仓 `git diff --check` 通过。

## 验证方法

原测试工具会丢失 bluetoothctl 扫描窗口、复用旧随机 MAC、丢分片日志，
投屏负载线程还与日志线程争读串口。修复后的 `ble_connect_test.py`：
使用 Bleak 实时广播回调，每轮按当前广播重新取地址；按 UUID 解析 GATT；
串口始终只有一个读取者；保存完整文本、原始字节、块时间戳与 JSON
结果；判成功必须看到本轮板端校时确认和完整存活观察。

```bash
systemctl --user stop ai-watch-viewer
/usr/bin/python3 tools/ble_connect_test.py -n 5 --scan-s 20 --hold 45 \
  --gap 5 --load none --log-prefix /home/ma/huangshan-logs/ble_4880_nc_none
```

该 A→B→A→B 对照支持共享环缓存属性是此次故障的关键原因。它是移植层
长期存在、由负载/时序改变而暴露的缺陷，能解释为何应用 BLE 文件基本
没改，却随其他功能开发反复退化。

光感、IMU、ADC 与 UI 已在候选镜像上正常运行；完整产品功能验收不包含
在本次 BLE 回归中。串口日志没有直接捕获到同一缓存行被双核覆盖的瞬间，
机制依据是源码的所有权冲突、厂商内存属性与重复镜像 A/B。
