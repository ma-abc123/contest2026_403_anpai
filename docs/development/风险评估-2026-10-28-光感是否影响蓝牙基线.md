# 风险评估 2026-10-28：光感（LTR-303）会不会影响蓝牙基线？

> 背景：用户担心"做光感会崩蓝牙基线，之前不稳过很多次"。
> 本文用代码级证据 + 量化数据，把"会崩 / 不会崩 / 不确定"三类分开，不写空话。

---

## 0. 直接回答

**不会。** 光感与蓝牙在代码、内存、总线、时序上**没有任何交集**，这一点可以证明，不是猜测。

但**有一个真实风险不在蓝牙，在 IMU**——如果处理不当，光感读写会拖慢 IMU 采样，进而影响跌倒检测。这个风险可控，且第 0 步（点灯）完全碰不到它。

---

## 1. 为什么"看起来相关"其实不相关：一条完整的证据链

之前 BLE 崩溃时，老板教过的教训是「看到 BLE 异常，先量这次改动有没有增加栈/堆占用」（P1-1 §2.2）。按这个方法论逐项核对：

| 检查项 | BLE 基线敏感？ | 光感会影响？ | 依据 |
|---|---|---|---|
| **SRAM 静态占用 / `.bss`** | **是**（邮箱窗口 0x2007FC00 被踩 = 控制器崩） | **否** | 光感驱动只有几十字节私有结构，且只有 `lux` 值；更重要的是：**驱动可以完全不加新静态 RAM**（局部变量 + 一个 pthread） |
| **HCPU↔LCPU 共享邮箱** | **是** | **否** | 光感不碰 0x2007FC00，不碰 IPC 环，不碰 `HCPU_TOP_RESERVED` |
| **LCPU 补丁 blob / 控制器复位** | **是** | **否** | 光感在 I2C1，与 LCPU（另一颗核）无关 |
| **zblue / HCI / h4 层** | **是** | **否** | 光感不调用任何 `bt_*` API |
| **LVGL 主循环阻塞** | 间接（阻塞 → 触摸死） | **否**（必须遵守） | 光感读放后台线程，不碰主循环 |
| **motion 线程栈** | **是**（4.9 就是栈越界踩坏堆） | **否** | 光感自己一个线程，**不改 motion 线程栈** |
| **I2C1 总线时序** | 否（BLE 不走 I2C） | **是（打 IMU）** | ← **唯一真实接触点** |
| **PA30 传感器供电** | 否 | **是（共用）** | 光感与 IMU 共用 HR3V3 |

**结论：9 项里有 7 项完全不碰，1 项（LVGL 主循环）只要按规矩做就不碰，1 项（I2C1）是必须处理的真实风险。**

## 2. 那唯一的真实风险：I2C1 总线已经被 IMU 占满 168%

这是本次评估最重要的发现，也是我上一轮判断"风险中高"却没说清楚的量化依据。

### 2.1 实测与推导

当前基线（4.8.23-p02 / 4.8.25-persist）的 IMU 读取路径：

```
lsm6dsl_sensor_read()          ← 一次六轴读
  └─ 17 × lsm6dsl_readreg8()   ← 逐个读 17 个字节寄存器（nuttx/drivers/sensors/lsm6dsl.c:853-960）
       ├─ i2c_write()          ← 加锁 #1
       └─ i2c_read()           ← 加锁 #2
```

即：**每轮采样 = 17 寄存器 × 2 次独立加锁 = 34 次总线加解锁** [A]。

| 量 | 值 | 来源 |
|---|---|---|
| 每轮事务数 | **34 次** | 代码统计 [A] |
| 实测每轮耗时 | **~42 ms** | P1-1 日志实测 [A] |
| I2C 速率 | **400 kHz** | `CONFIG_LSM6DSL_I2C_FREQUENCY=400000` [A] |
| 17 次读的**纯传输**时间 | **2.08 ms** | 400kHz 下按位长算：(3B×9+2)/400k ×17 ≈ 2.08ms |
| 因此**事务开销** | **39.9 ms（95%）** | 42 − 2.08 |
| 分摊到每次加锁 | **≈1.17 ms/次** | 39.9 / 34 |

**这意味着：42ms 里只有 5% 是真在传数据，95% 是锁、外设使能、HAL 调用的固定开销。** 而 `ai_watch_motion.c` 的采样周期是 `MOTION_PERIOD_MS = 25`——**一轮事务 42ms > 周期 25ms**。

**总线占用率 = 42/25 = 168%。总线本来就是超载的**，采样线程实际上一直在排队、被拖到约 15Hz（与实测吻合）[B]。

### 2.2 这个发现改变了两件事

1. **光感插进去一定会排队**，而且不是排在"空闲"里，是排在一条已经在超载的队列后面。单次光感读约 2.4ms，1Hz 只占 0.24% 占空比——**占比极小，但等待时间不可控**（最多等到 IMU 那一整轮 42ms 让出总线）。
2. **超时不是 1000ms，是 5000ms**（`sifli_i2c.c:41` `I2C_XFER_TIMEOUT = 5000`）。playbook 里写的 `I2C_TIMEOUT_ADDR/BUSY 各 1000ms` **与实际代码不符**，这条要更正——影响是：**一旦排队排崩，代价是 5 秒不是 1 秒**，IMU 会报 `-EIO` 并 `HAL_I2C_Reset`，跌倒检测出现 5 秒空洞。

### 2.3 但反过来看，这也是个机会

95% 的开销花在"34 次加锁"上，而不是传输上。如果将来把 IMU 改成一次 burst 读 12 字节（P1-1 已经做过、代码在 patch 里），**总线占用能从 168% 降到个位数**，那时光感、地磁、甚至 50Hz 采样都能一起上。

**所以正确的顺序可能是：先把 IMU 的 burst 读单独摘出来落地（它与光感无关、且不改变内存布局），再上光感。** 但这条属于额外收益，不是前提——见 §4 的方案对比。

## 3. 为什么我还是敢说"不会崩蓝牙"

因为**蓝牙不在这条总线上**。下面这条证据链是硬的：

1. BLE 的数据路径是 `应用 → 桥接 → zblue → H4(/dev/ttyHCI0) → LCPU 控制器`（`ble.md` 架构节）。
   **全程没有 I2C。** LCPU 与 HCPU 之间走的是共享 SRAM 邮箱 + HCI 环，不是传感器总线。
2. 光感读再多、再慢，最坏情况是 **IMU 采样变慢 / IMU 驱动报 -EIO**。这两件事对 BLE 的唯一影响路径是「栈溢出踩坏堆或者插新的静态 RAM」——而光感驱动可以做到**零新增静态 RAM**（局部变量 + 一个后台线程）。
3. 历史证据也吻合：4.9 那 21 个 bin 里，**凡是崩 BLE 的都是改了内存布局或栈大小的**（§2.2 的栈越界、P0 的堆布局变化），**没有一个是"因为多了个 I2C 设备"而崩的**。

**换句话说：你怕的那种崩，触发条件是"动了内存"，不是"动了总线"。光感不满足那个触发条件。**

## 4. 三个安全等级，按你的风险偏好选

你说"只要能影响一点东西都怕"，所以我把它拆成三档，**第 1 档连总线都不碰**：

### 档 1：只验证，不改任何行为（零风险）

- 只做"点灯"：开机读一次 0x29 的 Part ID，串口打印一行 `LTR303: partid=0x86`。
- **读完就关，不启线程、不周期读、不接 UI**。
- 风险：**理论零**。唯一开销是开机时多一次 ~2.4ms 的 I2C 读，发生在 IMU 线程启动之前。
- 产出：确认"这颗芯片在不在、地址对不对"。**这一步的答案决定后面要不要继续。**

### 档 2：周期采样 + 串口打印，不接亮度（低风险）

- 起一个独立后台线程，1Hz 读 lux，只在串口打印。
- 给 IMU 采样线程加一把**应用层总线锁**（见 §5.1），保证光感读不会插进 IMU 单次 `sensor_read` 中间。
- 风险：低。即使出问题，症状是"IMU 采样率下降"这种**可观测、可回退**的现象，不是崩溃。
- 回退：删掉线程启动那一行即可，零残留。

### 档 3：接到亮度 → 自动亮度（中风险，但收益最高）

- lux → 分档映射到 5 档亮度，带滞回，手动优先。
- 风险：与档 2 同源（都是总线时序），**没有新增风险类型**。但多了"亮度抖动导致 UI 观感差"这种体验问题。
- 前提：档 2 连续跑一天不出现 IMU 采样异常。

**我的建议：先走档 1，看结果再决定。** 如果 Part ID 读不到，整个方向的投入就到此为止，一分钱不浪费。

## 5. 如果继续做，必须遵守的四条硬约束

### 5.1 用应用层锁保护"整轮 IMU 读"，不是保护单次读写

当前 NuttX/SiFli 的锁是**逐次 `transfer` 级别**的（`sifli_i2c.c:485` 加锁 / `:571` 解锁）。也就是说 IMU 的 17 次 `readreg8` 之间是**开放的**——光感完全可以插进第 8 次和第 9 次之间。这本身不会损坏 IMU（每次读都是原子的），但会让一轮 42ms 被拉长，采样时间戳变散。

**做法**：在 motion 线程里用一把应用层 mutex 包住**整个 `sensor_read()` 调用**，光感线程读之前抢同一把锁。

```c
/* ai_watch_motion.c 采样循环内 */
pthread_mutex_lock(&g_i2c1_app_lock);
ioctl(fd, SNIOC_LSM6DSLSENSORREAD, &data);
pthread_mutex_unlock(&g_i2c1_app_lock);
```

**这把锁必须按"整轮"持有**——如果只包单次 transfer，等于没加。这是最容易做错的地方。

### 5.2 绝不违反红线 #2：探测不能在主循环

对不在线的 I2C 设备探测一次 = 阻塞最长 **5000ms**（实测代码值，比 playbook 写的 1000ms 更糟）。所以：

- **绝不在 LVGL 主循环里 open/read 光感**。
- 探测只在启动时做一次（此时 IMU 线程还没起，风险最低）；失败就**永久放弃**，不要退避重试。
- 真要重试，必须照 playbook 的 PENDING/ABSENT 三态 + 100ms 切片模式走后台线程。

### 5.3 不加静态 RAM

- 驱动私有结构放 `.bss` 会让 SRAM 静态值变化，**这正是 BLE 最敏感的量**（虽然理论上几十字节不影响邮箱窗口，但没必要冒险）。
- 做法：驱动里用**局部变量 + 一个 pthread 栈**（8KB 够），lux 值直接写进已有的 BLE 上报结构或 motion 快照，不新增全局数组。
- **验收方法：构建后必须看到 `sram: 311,316 B` 不变**——这是 p02/persist 两版都没动过的值，一旦变了就是亮了红灯，立刻停下来看。

### 5.4 1Hz 是上限，不要贪快

人眼适应亮度以秒计。2Hz 已经是过度设计。**采样越快，撞上 IMU 事务的概率越高，纯属自找麻烦。**

## 6. 必须更正的两处既有记录（本次发现）

1. **`sifli_i2c.c:41` 的 `I2C_XFER_TIMEOUT = 5000`（5 秒）**，而 playbook `sensors-i2c.md:5` 与 `SKILL.md` 红线 #2 都写"`I2C_TIMEOUT_ADDR/BUSY` 各 **1000ms**"。
   - 影响：所有"探测阻塞 1-2 秒"的估算**低估了 5 倍**。
   - 这不改变"探测要放后台"的结论（结论更强化了），但改变了"最坏情况可接受"的判断——**5 秒的冻结在手表上是不可接受的**。
2. **I2C1 已超载（168%）** 这件事此前没有任何文档记录。`决赛打磨计划` 里"IMU 链路 833Hz → 实际 ~15Hz，I2C 逐字节读（22 次/帧 ≈42ms）是根源"只说了原因，没说**占用率超过 100%** 这个事实。这解释了为什么 4.9 一提速就必然崩——**不是提速本身有问题，是总线早就没有余量**。

---

## 7. 一句话给决策

> **光感不会崩蓝牙**（不同总线、不同内存、不同代码路径，7/9 项零接触）。
> **光感可能拖慢 IMU**（I2C1 已超载 168%，插任何东西都是排队），但这是**可观测、可回退**的性能问题，不是崩溃。
> **先做档 1 点灯验证**，Part ID 读到了再往下走；读不到就整条线砍掉，零损失。

风险最低的完整路径其实是：**先单独把 IMU burst 读落地**（它把 34 次加锁变 2 次，总线占用从 168% 降到个位数，且不改变任何内存布局），**再上光感**。到那时光感和 50Hz 都不再是问题。但这属于"先修地基再说装修"，要不要这么排，你定。
