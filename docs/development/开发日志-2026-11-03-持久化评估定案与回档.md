# 开发日志 2026-11-03 — P1-3 flash 持久化：评估定案（不做）与代码回档

> 版本：4.8.62-nostore（持久化代码已回档移除）｜ 基线：4.8.57-perf5（`contest/ai-watch`）
> 结论先行：**P1-3 本板做不了，决定不做**。固件从 NOR XIP 执行，而厂商 QSPI 驱动
> 只有「独占 flash」一种工作模式：要么写的时候打死取指，要么手工命令根本不落盘。
> 整条实现已**回档移除**（不是开关关闭），代码存档在本地分支
> `backup/p13-store-f74d0eb`，将来厂商修好或换介质可直接取回。
> 现场证据全部留存于 `~/huangshan-logs/store*_*.log`，flash 内容用 sftool 直读校验。

## 1. 需求与设计（曾完整实现，现已随回档移除）

| 项 | 实现 |
|---|---|
| 当天步数/活动/跌倒摘要 | `/dev/config0` 扇区 0 的 append-log：`magic+seq+len+crc`，新记录挤不下才擦扇区；最新有效记录胜出 |
| 跌倒证据（前后 30 s 原始六轴） | 双槽（每槽 10 扇区 = 40 KB）：头 28 B + 38 400 B 环形窗口；**头最后编程**做提交标记；`sent` 字节 0xFF→0x01 原地改写 |
| 个性化阈值存储（P2-3） | 扇区 1 的 config append-log，opaque payload |
| 固定占用 | 约 85 KB，不随运行时间增长 |
| 写线程 | 独立 pthread 持有设备，擦除绝不阻塞主循环（红线 1） |
| 跌倒环形缓冲 | `g_evring` 2400 样本（60 s@40 Hz），armed 冻结前 30 s，confirm 后 30 s 封存 |
| BLE 补发 | 断线重连后 5 s 一次探测未发送事件，`has_unsent_fall → post → mark_sent`（限流，避免 10 ms 主循环里读 NOR） |

顺带修掉的两个真 bug：
- 原实现用 `ioctl(MTDIOC_ERASESECTORS)` 擦除，但 `sf32lb_nor_ioctl` **没有这个 case**，只会返回 `-ENOTTY`；改为 `MTD_ERASE()`。
- `mark_fall_sent` 把 `sent` 字节写成硬编码偏移 24，实际是 27（24 是 `falls_today`）；改为 `offsetof()`。

## 2. 三处阻断（按发现顺序，都带测量）

### 阻断 A：`open("/dev/config0")` 必崩 —— 走了 BCH/FTL 块代理

- 现象：boot 后 `KEY2 button monitor started` 紧接着 hardfault，`STORE:` 一行都没有（store1）。
- 定位：探针把崩溃夹在 `open()` 内；`fs_open.c` 对 `INODE_IS_MTD` 走 `block_proxy()`
  → `ftl_initialize_by_path()`，即把裸 MTD 当成**磨损均衡块设备**（语义完全不对，还会
  改写扇区头），这条路径直接崩。
- 处置：改用 `find_mtddriver()` + `MTD_READ/MTD_WRITE/MTD_ERASE` 直调，绕开 VFS 代理。

### 阻断 B：`MTDIOC_GEOMETRY` 里的厂商 `HAL_FLASH_PreInit()` 打死 XIP

- 现象：`ioctl` 内部必崩；若前后多打几行 printf 又「能过」，换编译就复发（Heisenbug）。
- 测量（nuttx 里临时加 hardfault 探针，事后已回退）：
  ```
  HFDBG pc=120a08ba lr=120a088d
  cfsr=01000000  hfsr=40000000
  ```
  `CFSR=0x01000000` = **IBUSERR（取指总线错误）**，PC 落在 `flockfile`（printf 内部）。
  解释：`HAL_FLASH_PreInit` 会重写 AHB 读配置（TIMR/CIR/ABR1）、重设分频（PSCLR=1）、
  再给 NOR 发 RST；此后**第一次冷取指**就死。之前「能过」是因为那段代码已被缓存、
  且中间插的 printf 顺手把 `flockfile` 预热了。
- 结论：**只要 CPU 从这片 NOR 取指，就不能调 `HAL_FLASH_PreInit`。**

### 阻断 C：不调 PreInit，手工命令通路也不工作

按「保留启动时的控制器配置、只补句柄字段」改写 `preinit_runtime` 后（JEDEC id 读到
`0x18400b`，16 MB，几何 1024×4096 正常），又发现：

1. `HAL_FLASH_CONFIG_AHB_READ(hflash, true)`（厂商的「恢复 quad 读」）**单调用就会打死 XIP**。
   表里 4READ = `cmd 0xeb / dummy 4`，与本板启动配置不一致。
   → 改为**开机快照 MPI 控制寄存器、操作完原值回写**（`sf32lb_flash_restore_mpi`），
   XIP 存活，写入流程能跑完并返回。
2. 但**数据没写进 flash**：`verify` 读回是常数 `5ff800f0 5ff800f0`；
   用 `sftool read_flash` 直读 `0x129A0000` 证明数组**一个字节都没变**（前后两次 dump 完全相同）。
3. DMA 页编程路径写进去的是垃圾（32 字节全错）；关掉 DMA 走 FIFO 路径后仍然不落盘；
   补回 `HAL_FLASH_CLR_PROTECT`（清写保护）也无效。
4. 手工 0x03 读命令返回常数，说明**手工命令通路本身没被正确配置**：厂商靠 PreInit 的
   TIMR/CIR/PSCLR 才让它工作，而这些寄存器正是 XIP 的配置——两者不可兼得。
   另有一层：任何手工命令都会让 NOR 退出「连续读」状态，而重新武装所需的配置又与
   启动配置不同，快照回写只能复原控制器、复原不了芯片侧状态。

## 3. 定案

- **不做持久化，代码回档移除**（2026-11-03 决定）。曾考虑「保留实现 + 开关关闭」，
  但那只是在仓里留 900 行永不执行的代码 + 一份 57 KB 的 PSRAM 预算，答辩也用不上；
  实现存档在分支 `backup/p13-store-f74d0eb`，需要时整段取回。
- 要走通需要**厂商级改动**，二选一：
  1. 一条「不依赖 XIP 的 flash 操作通道」：整段（配置→编程→复原）纯 RAM 执行，
     且能正确复原芯片侧连续读状态；难点是 PreInit 内部 `spi_flash_get_cmd_by_id()`
     在 flash 里，执行到它就死。
  2. 换介质：另一片 NOR/SPI flash（另一控制器）、或 TF 卡。
- 已排除：littlefs（同一个驱动、同一个问题）、RTC 备份寄存器（掉电即失）。

## 5. 答辩表述（替换原来的「事后可回溯」说法）

原来打算讲「跌倒前后 30 s 原始数据落盘，事后可回溯」。本板做不到，改成可验证的说法：

1. **能力边界讲清楚**：从 NOR XIP 执行的固件无法在运行期编程同一片 die，
   这是硬件/驱动约束，不是没实现——附 `CFSR=0x01000000 IBUSERR` 与
   `sftool read_flash` 前后一致的证据，反而体现排查深度。
2. **现有能力讲足**：跌倒检测全链路（六轴 40 Hz → 冲击/失重/姿态 → 15 s 全屏倒计时
   → 可取消 → BLE 上报）、当日步数/活动/夜间起夜在会话内统计。
3. 若评委追问持久化：明确说「等真机换介质（TF 卡或第二片 flash）即可落地，
   设计与代码已经验证过一遍，存档在分支里」。
