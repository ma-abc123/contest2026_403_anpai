## 1. M4 运动服务与跌倒检测（4.8.0）

### 1.1 架构

新增 `app/ai_watch/ai_watch_motion.c/h`：后台 pthread 独占 `/dev/lsm6dsl0`（板载 LSM6DS3TR-C，bringup 已注册，revid 实测在位），`SNIOC_START` 后以 25ms 周期 ioctl 轮询（驱动无 ODR 接口，内部固定 833Hz），**全部 DSP 在采样线程内完成**；LVGL 主循环只通过 mutex 保护的快照消费结果——延续心率页探测线程的防撞锁模式。服务开机自启，跌倒检测与 UI 无关。

实测采样率 **~15Hz**（25ms sleep + ~42ms ioctl，22 次单字节寄存器读的 HAL 开销）。对冲击检测偏低的采样率是已知限制，靠下文的"自由落体门控 + 平落路径"补偿；burst 读优化留作后续。

### 1.2 跌倒判定（最终阈值，全部经实机数据回归）

三状态机 `NORMAL → IMPACT → ALARM`：

- **冲击门**（任一）：单点 >`2400mg`；连续两点 >`2000mg`；自由落体采样（<`550mg`，单样本即锁存，`FALL_FREEFALL_MG`）后 500ms 内单点 >`2000mg`
- **确认门**（静止窗末 1s 波动 ≤`80mg` 后检查，观察预算 `10s`，每 1s 复查）：
  - 翻转路径：重力方向变化 ≥`50°`（跌倒前姿态 = 快速重力 LPF 冻结，α=0.15，约 1s 收敛）
  - **平落路径**：翻转不足但有自由落体前科 + 持续静止 ≥`4.5s`（"掉落而非放置 + 无人捡起"）
- 告警后 15s 倒计时（`AI_WATCH_FALL_COUNTDOWN_MS`），KEY2 或全屏按钮取消；超时上报 `FALL_EVENT`（f3，event=1 确认/2 取消/3 测试），文案一律"疑似跌倒"
- 冷却：告警结束后 60s，**拒绝后仅 8s**（`FALL_REJECT_COOLDOWN_MS`，否则"砸→拿起→再砸"的测试节奏会被吞）

### 1.3 Exercise 页与采集

Exercise registry 项激活：步数（|a| 迟滞峰值检测 1150/850mg、300ms 不应期、步长 0.7m）、活动分类（2s 窗 std：<30 静止 / >350 跑步 / 其间步行，1s 防抖）、实时 |a| 条、Record/Test 按钮。Record 原始数据双通道：串口 CSV（`REC,t_ms,x,y,z,gx,gy,gz` 全量）+ BLE f3 `0x12`（每 4 条转发 1 条）。

分析脚本 `tools/fall_threshold_analysis.py`：解析串口日志（t_ms 归零自动切会话），回灌**与固件同一套**状态机，输出冲击/角度/检出与 PASS/FAIL（文件名含 fall=期望触发）。**重要教训：脚本与固件曾一度不是同一算法（初值不同导致角度结果 131° vs 34°），现已严格镜像，离线调参结论才可信。**

## 2. Record 触控冻结（4.8.1）

**现象**：点 Record 后 Stop 点不了、触控全死，KEY2（主循环 GPIO 轮询）正常。

**根因**（日志实锤）：REC 时间戳节拍 `40/43/172ms` 交替——每第 4 条样本（即每次 BLE MOTION_DATA 发送）主循环停顿 ~120ms。`bt_gatt_indicate` 在本移植上同步等待对端确认（≈1 个连接间隔），6~8 次/秒的发送吃掉主循环 60-70%，LVGL 触摸采样失效。

**修复**：`ai_watch_ble_post()` 异步发送——48 深帧队列 + 专用 TX 线程（`ai_watch_ble_init` 启动），失败固定退避 2s。MOTION_DATA/STEPS/ACTIVITY/FALL_EVENT 及 DHT、HR/SpO2 全部改走异步；**仅 AI 触发保持同步**（按钮需要发送结果）。同时治好了首连 STEPS 重试风暴（4.8.0 日志 119 条 "not subscribed" 刷屏 → 现最多每 2s 一条）。

## 4. BLE 连接必崩：LCPU legacy patch blob 过时（4.8.4-exp1）

### 4.1 现象与定位

4.8.3 起**任意 central（AI App 与通用蓝牙工具）连接后 0~2s 控制器断言**，4/4 复现、跨两次重启：

```
aiwatch-ble: connected
<err> Hardware error, hardware code: 0
lcpu evidence: revid=3 (legacy patch path) assert_over=2 ai=54b3f5ef d0fd15a1 aacb3edf 053c5c0f cfg=45457878 ...
aiwatch-ble: disconnected, reason 0x00
→ HCI_RESET 自愈 → 恢复广播 → 再连再崩
```

排查排除项：应用层 diff（B→C 仅运动算法三处）、我方 BLE 流量（崩溃先于任何成功发送）、heap arena/LCPU 邮箱窗口（两次启动均 8457112）、手机 App 因素（换通用工具同样崩）。08:39 同宿主行为连接成功 vs 08:49 必崩的对照曾指向手机侧，最终由外部审计推翻。

### 4.2 根因（外部协助审计）

`sf32lb52_lcpu_boot.c` 的 legacy 路径（`revid=3 < HAL_CHIP_REV_ID_A4`）include 的是 `middleware/.../sf32lb52_lcpu_patch.h` 里的**旧 blob**（2024 words/8096B，头 `F001FE67/4805F8DF`）；而仓库 e1cc823 同步的新版 blob（2040 words/8160B，头 `F001FE87/4805F8FF`）躺在 `chips/drivers/cmsis/sf32lb52x/lcpu_patch.c` **从未被 legacy 路径加载**。公开 SDK 变更日志中该 blob 含 `fix 52X ble connection update dump issue` 与 `fix 52 bt controller ld stop assert`——与"连接后 LL 控制过程期间 LCPU 上报 Hardware Error"精确吻合。

### 4.3 修复与验证

- 新增 `sf32lb52_lcpu_patch_exp.h`（新 blob 原样拷贝，二进制级验证已链接、旧 blob 不在镜像；8160B < 8KiB 补丁区，与旧 blob 同样贴边无新风险）
- `sf32lb52_lcpu_boot.c` include 切换（一行，可回退）+ `sf32lb52_lcpu_boot_dump_evidence()` 读前 `up_invalidate_dcache()`（0x2040FDA0-0x2040FDE0，此前可能读到 cache 旧值）
- **实机验证：蓝牙连接恢复 ✅**（4.8.4-exp1，`size_slim_20260829/final_484_exppatch_nuttx.bin`）
