# 决赛打磨计划（2026-10-24 起）

> 阶段：决赛打磨 ｜ 基线：v4.8.5（contest/ai-watch @ aca66d2）
> 数据来源：nuttx.map 实析、板端启动日志（ai-watch-20260902-144040.log）、defconfig、rcS、源码走查（2026-10-24 盘点）；
> P0 部分另依据《固件瘦身与BLE自愈记录-2026-08-30.md》历史实测与回退史（2026-10-24 复核）

## 0. 现状快照（决策依据）

| 资源 | 总量 | 当前占用 | 结论 |
|---|---|---|---|
| Flash | 16 MB | 5.1 MB（32%） | 宽裕，可放数据日志分区 |
| SRAM | 512 KB | 静态 403 KB（79%） | 真瓶颈，其中 allsyms 130 KB 纯浪费 |
| PSRAM | 8 MB | 已启用并入 malloc 堆（共 8.4 MB） | 堆不受限，但 QSPI 速度低于 SRAM |
| CPU | 单核 Cortex-M33，无 NPU | — | 端侧只做手写 int8 小模型 |
| IMU 链路 | 芯片内部 833 Hz | 实际 ~15 Hz | I2C 逐字节读（22 次/帧 ≈42ms）是根源 |
| BLE | LCPU + zblue | indicate 同步阻塞 ~120ms/次 | 高频上报受限，TX 线程方案保留 |
| 音频 | 无麦克风 | — | 语音只能留在手机侧 |

关键事实：

- quickapp/QuickJS/curl/freetype/UIKit 全家桶被链接但**运行时永不执行**（rcS 仅在 `#ifndef CONFIG_EXAMPLES_AI_WATCH` 时启动 vapp）。**此结论有实机先例**：2026-08-30 曾整组裁掉（flash -2.7MB、SRAM -108KB，分组实机验证通过），后因连环显形问题在 M4 冲刺期保守回退；其中"删 ROMFS 演示资源"一步（-2.76MB）保留至今。当时显形的 4 个问题（堆覆盖 HCPU↔LCPU 邮箱窗口、init 栈溢出、RTC 2036 垃圾值、zblue send_sync 悬空栈）的修复**均已固化主线且与瘦身开关无关**（2026-10-24 已逐一复核在位：`HCPU_TOP_RESERVED`、`CONFIG_INIT_STACKSIZE=65536`、RTC 年份守卫、`hdev->sync_sem`）。
- `CONFIG_ALLSYMS=y`+`CONFIG_ELF=y` 拉入的 130KB 符号表：**历史瘦身从未动过它，属无先例项**，只进 P0-1 可选试验组，不承诺收益。
- LSM6DS3 的 INT1 引脚**已接线到 PA31**（bringup 已配 GPIO 输入），驱动未使用；FIFO 寄存器定义在头文件里齐备，驱动未用。
- `/dev/adc0` 已初始化带校准——电量显示可行。
- 启动日志有 WARN：XIP bringup 阶段 `HAL_FLASH_Init` 被跳过、NOR 写擦禁用——**持久化落地前必须实测 `/dev/config0` 可写性**。
- CJK 显示走编译进固件的 `ai_watch_font_cjk_16`，与 `CONFIG_LV_USE_FREETYPE` 无关（关掉不影响中文）。
- 遗留物：DHT22 驱动仍在注册（功能已于 4.8.5 移除）、`CONFIG_EXAMPLES_LSM6DSL_READER=y` 仍开启。

## 1. 总体策略

**先减后增**：P0 砍死重释放资源 → P1 打采样与持久化地基 → P2 端侧模型与算法升级 → P3/P4 手机 AI 与安全闭环 → P5 体验与演示打磨。

依赖关系：P2 依赖 P1（采样高、数据多，模型才训得动）；P0 与一切并行无冲突；P3 的手机侧生成可独立推进，手表负一屏 UI 建议在 P0 瘦身完成后动工（SRAM 余量更足）。

每项完成后照例：bump `AI_WATCH_VERSION`、烧录前备份 bin、开发日志（含根因）、算法改动同步镜像离线脚本、公共仓改动走 fork + PR。

### P0-1 defconfig 瘦身（按 2026-08-30 历史分组重放，非一把梭）

**前史**：本轮瘦身 2026-08-29/30 已完整做过一遍（《固件瘦身与BLE自愈记录-2026-08-30.md》），分组"关闸→重配→构建→烧录"实机走过；后因显形问题保守回退，但当年的修复已全部固化主线（见现状快照）。**因此 G1~G6 是有先例的重放，不是未知尝试。**

**执行方式**：复刻当年 `step3_group.sh` 思路，逐组关闭→全量重配构建→bump `AI_WATCH_VERSION`→烧录→跑回归清单；每组留存独立 bin，出问题只回退该组，不整批放弃。

**预期收益**（G1~G6，按历史实测推算当前体量）：flash 5.1MB → 约 2.4~2.7MB，SRAM 静态 403 → 约 295KB；试验组若通过再省 130KB SRAM，**不计入承诺**。

**每组实机回归清单（覆盖当年爆雷场景，缺一不可）**：
1. 开机 UI/时间/触摸正常；校时前后时间均非 2036 垃圾值（当年 RTC 爆点）
2. BLE 连接→订阅→校时→提醒横幅；连接后**立即开 Reminder 页**（当年栈溢出爆点）
3. 手机两次快速断连重连，无 `Hardware error`/oops（当年邮箱窗口爆点）
4. 彻底断电重启后全链路复测（当年只在断电后暴露）
5. 跌倒 Test 路径、计步/活动页、中文标题渲染正常

**残余风险**：堆/栈布局变化仍可能显形**新的**潜伏问题（历史上即如此）——这正是逐组烧录的意义；当年修复在位只保证旧雷不复发，不保证零新雷。

## P1 数据与采样地基（1~2 周）

### P1-1 lsm6dsl burst 读（nuttx fork PR，P1 核心）

- 从 `OUTX_L_G` 起一次 12 字节事务替换 22 次单字节读；读前查 `STATUS_REG` DRDY
- 预期：单帧读取 ~42ms → ~3ms，应用层轮询 25ms 即可稳定 50~100 Hz（`MOTION_PERIOD_MS` 相应下调）
- 流程：从上游 `dev-ai-contest-2026` 新开分支改 `nuttx/drivers/sensors/lsm6dsl.c`，`git am` 到本地验证后发 PR
- 验收：串口 MOTION 时间戳实测 ≥50 Hz；`fall_threshold_analysis.py` 回归全绿（阈值可能需按新采样率重定标）

### P1-2 芯片硬件检测器利用（分两档，按时间取舍）

- 档 1（低成本）：轮询 LSM6DS3TR-C 内置 free-fall / activity / wake-up 标志寄存器，自由落体锁存由软件单样本判据换成硬件标志
- 档 2（完整）：INT1（PA31，已接线）真中断 + FIFO 排空读取——833 Hz 满采样 + 事发前数据自动在 FIFO 里
- 验收：档 1 一并纳入回归；档 2 需新增测试集重新定标（采样率数量级变化）

### P1-3 flash 持久化

- 先实测：XIP WARN 影响下 `/dev/config0`（1024 blocks）能否挂 littlefs 并读写
- 实现：每日步数/活动摘要一行制；跌倒事件落盘时附带**前后 30 s 原始六轴环形缓冲**；重连 BLE 补传手机
- 验收：断电重启数据不丢；补传在手机 FallRepository 落地

### P1-4 测试集扩充 + 一键回归

- 6 组 → 15~20 组：上下楼、快速坐倒、拍打手表、跳跃、骑车颠簸、平放拿起等
- `tools/fall_threshold_analysis.py` 增加全量批跑模式，输出总表；此后任何阈值/算法改动先跑回归
- 验收：负样本 0 误报、正样本全检出（或明确记录取舍）

## P2 端侧 AI 与算法升级（2~3 周，决赛差异化主打）

### P2-1 特征与训练管线

- 特征：自由落体时长、冲击峰值/宽度、静止窗 std、重力方向角变化、跌倒前活动状态、冲击后静止时长
- 树内无 TFLite，路线定为：sklearn 训 GBDT/浅决策树 → 导出 int8 C 数组 → 端侧手写推理器（预计几百行）
- 验收：离线在全部测试集上 ROC 优于现有规则状态机

### P2-2 端侧分类器上板

- 规则状态机保留为安全护栏与可解释基线；模型输出与规则融合（任一触发即进入告警，模型可下调误报）
- 权重/查找表放 PSRAM 或 flash，推理 1 Hz 级频率
- 验收：上板回灌全部测试集；演示页可切换 规则/模型/融合 三模式（答辩演示点）

### P2-3 个性化自适应阈值

- 开机静置 N 秒校准重力基准；运行期学习佩戴者步行冲击分布与静止噪声底，安全界内（±15%）自动微调并存 flash（依赖 P1-3）
- 验收：两名以上不同佩戴者数据对比，误报/漏报方向性改善

### P2-4 活动识别升级（可选）

- 3 类 std 阈值 → 小特征窗口分类器（静止/步行/跑步/上下楼/颠簸），复用 P2-1 管线

## P3 AI 信息服务（手机生成 + 手表负一屏呈现，约 1 周，与 P1/P2 并行）

> 2026-10-24 决策：**"跌倒 AI 溯源报告"不做**（跌倒事件以确定性参数呈现即可，见"明确不做"）；每日简报升级为**手表侧 AI 负一屏**，作为本阶段主打。

### P3-1 AI 负一屏 · 每日简报（主打项，跨手机/手表两仓）

**手机侧**（phone/ 仓）：

- 聚合当日步数/活动分布/跌倒（+夜间数据若 P1-3 落地）→ LLM 生成简报 → 推送手表
- 时机：每日晨间对时后自动生成 + 手机端手动刷新按钮（演示友好）；断网跳过本轮不崩溃
- 协议：新增 Command `AI_WATCH_BLE_CMD_DAILY_BRIEF`（0x06）**结构化载荷**：`[日期][步数][活动分钟][事件数][评语文本]`——原生字段 + 短评语，不走长文本；可重复下发覆盖最新一份（天然幂等，不受 `AI_TEXT` 224 字节上限约束）

**手表侧**（app/ai_watch）：

- **负一屏入口**：表盘左滑进入（与现有翻页/手势导航同向约定），KEY2 返回；作为固定页注册进页面管理器
- 原生渲染：日期与生成时间、核心数据行（步数/活动分钟/事件数）、AI 点评 1~2 句（CJK 16 号）；正在查看时收到新简报即时刷新
- 空态兜底：无简报/未连手机时显示本地统计（来自 motion 快照）+ "连接手机生成"提示——手表单独使用也有内容
- 实现约束：纯主循环线程渲染，数据源为 BLE process 写入的共享状态（红线 1/7 不破）；（可选）最新一份落 flash 依赖 P1-3，重启后仍可见
- 验收：晨间自动收到并展示；空态/断电重启后状态正确；评语文本长度在 CJK 16 号下不溢出（超长自动截断加省略号）；演示场景可现场手动刷新立即出结果

### P3-2 语音提醒增强

### P3-3 离线兜底 + 多轮对话（可选）

## 风险清单

1. **flash 写擦**（P1-3）：XIP WARN 可能挡路，第一天先实测，不行则改用 ROMFS 之外的方案或缩小范围（只在 BLE 在线时实时上报，本地仅存摘要）

4. **紧急联系人合规**（P4-1）：演示与真实使用都要显式授权与可关闭开关
