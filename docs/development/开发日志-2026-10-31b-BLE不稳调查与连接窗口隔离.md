# 开发日志 2026-10-31b — BLE 不稳调查（连不上 / 授时前 LOST）

固件：**4.8.46-remote**（bin 备份 `~/huangshan-logs/bin_484{3,4,5,6}_remote.bin`）。
前情：同日坏屏投屏链路改造（见本日 a 篇）之后，用户报告蓝牙"容易不好连接上，
容易在授时之前抛 LOST"。

## 用户原始疑问：是不是时序问题？

**是，且指纹与 10-26/10-27 已知的回归家族完全一致**——不是新病，是老病在
投屏时代的显形与叠加。

## 实测抓到的失败形态（主机 hci0 + 串口联合取证）

1. **连接后 ~300 ms 控制器死亡**：`connected` → `controller recovery
   type=hardware-error opcode=0x0000` → `disconnected, reason 0x00
   duration_ms=303` → 强制拆链。与 10-26 日志 §2.2 的"一连上就 Hardware
   error"（采样栈溢出踩堆 → HCPU/LCPU 共享内存 → 控制器崩）同指纹，
   也与 10-27 记录的 r13（~0.5s HW error 0x10）同族。
2. **boot bring-up 彩票**：自研 `tools/ble_adv_lottery.py` 反复上电统计，
   4.8.43 基线 **3/8 boots** 在 12 s 内广播可见；失败 boot 的取证显示
   首次 `bt_enable` 超时（-110）→ 强制拆链 → 重试链。部分 boot 广播
   迟到 10-25 s（+10 s 的 INIT_FAILED 恢复成功路径），部分 45 s 仍暗
   （wedge 深化，P1-1 §2.4：需长断电）。手机早于板子可连就放弃了
   ——这就是"容易不好连接上"的主体。
3. **断开后重广播 -11（EAGAIN）循环**：bridge 只对 -EALREADY 做了清理
   舞步，-11 落进 30 s 退避；后续常被 command-timeout 接力进 recover。

## 排查路上的一次反向教训（重要）

**给 INIT_FAILED 阶梯"前倾"（3/8/15 s 重试）让事情更糟：0/8 boots 在
45 s 内广播**（4.8.44 实测）。`bsp_recover()` 不是轻量探询，是完整控制
器拆链+重建（阻塞主循环 ≤10 s），每跑一次就重置 LCPU-release 竞争时钟；
3 秒一锤等于让竞争窗口永远归零。已回退并改为**温和前倾**（15/20/30/60/
120/300 s），实测 boot 3 的 +10 s 首次恢复在 16.4 s 上线、4.8.46 彩票
4/6（含 24.5 s 迟到案例）。**教训：对这套 fragile bring-up，"更快重试"
不是更强的恢复。**

## 本轮固件改动（全在应用仓，vendor/zblue 未动）

1. `ai_watch_ble.c`：INIT_FAILED 退避温和前倾（首试仍 +10 s，后续
   15/20/30/60/120/300 s），把"暗 boot"的典型恢复时间从 ~40-100 s
   拉到 ~25-45 s。
2. **连接窗口隔离**（10-26 日志的处方，R14 思路的落地）：
   `ai_watch_ble_connect_window_active()` = CONNECTED 且未授时（8 s 硬
   上限）。窗口内主循环：`ai_watch_shot_set_stream_gate(true)` 暂停帧流
   （主机端 1.5 s 超时自动补发，窗口结束自行恢复）+
   `ai_watch_motion_set_slow(true)` 采样降到 15 Hz（4.8.23-p02 验证过
   的安全速率）。窗口结束立即恢复。**掉电/未连接状态不受影响**（预览
   常开）。
3. 未动 TXBUFSIZE=2048。布局位移仍是嫌疑清单第一项（红线 14：ALLSYMS
   实验 46KB 位移曾引发 init wedge 风暴），A/B 方法已备好
   （`ble_adv_lottery.py`），若手机实测仍差再降回 256 对比。

## 追加（同日第三轮）：手机实测反馈与 4.8.47 的撤销

用户实测 4.8.46：首次连接抛一次 LOST → 恢复后能连上；**断开再重连就
永远失败**。投屏守护日志取证：死亡时机后移到连接后 ~4.5-5.3 s（紧跟
CCC 订阅/授时后的首批通知突发）；一次完整成功会话（ccc×2 → time
synced）之后又一起 hardware-error → teardown → 重初始化 → 用户侧再也
连不上（板端最后一行是 advertising as）。

4.8.47 曾试图用"DISCONNECTED>20s 升级 recover + 新鲜链路 2s 静默 +
断开清积压"对症，用户实测"蓝牙根本起不来"后按其要求撤销提交。
**按 ble.md"最强证据"标准，单次烧写的归因没有证据力**——4.8.47 的
app diff 经代码审计在"从未连上的 boot"里是惰性的（DISCONNECTED 分支
进不去），其失败与 4.8.46 一样落在 boot wedge 彩票上。

保留进 4.8.48-ble2 的两项（与 4.8.46 的差异仅此 + 版本号）：
1. **新鲜链路 2 s 静默**：连接后前 2 秒 TX worker 不发通知（首批通知
   突发与 4.5-5.3 s 死亡强相关）；
2. **断开即清空上行积压**：暗期积攒的陈旧遥测不在重连时爆发
   （已知竞态：与 TX worker 阻塞 notify 交错时可能重放一条，影响为
   陈旧数据而非崩溃）。

被撤销的"DISCONNECTED>20s 升级 recover"：recover() 是含 LCPU 热复位
的完整拆链，30 s 一次即是风暴放大器（P1-1 §2.4/§2.6 剂量态）；安全
策略按 4.5.0/4.8.10/4.8.18 三代实测记录 = 事件驱动单次 recover、
teardown 间隔 ≥10-15 s、由 INIT_FAILED 梯子与故障路径承担。

**4.8.48-ble2 用户实测：有提升（2026-10-31 深夜）。** 保留 TX 静默与
积压清理，撤销升级逻辑——与 ble.md"最强证据"标准的教训一致：版本
归因需要多轮 A/B，本轮为单次实测，后续遇到回归先用
`ble_adv_lottery.py`/`ble_connect_test.py` 留多轮数据再下结论。

另证：板子随机地址逐 boot/recover 轮换（62:9C:… → 4E:4B:…）——手机
若按缓存 MAC 重连必败，App 需按名称重扫；根治需 vendor 固定 identity。

## 追加（同日第四轮）：bridge 状态机审计——风暴主源与 vendor 修复清单

并行子代理对 `sf32lb52_ble_bridge.c` / `sf32lb52_bt_adapter.c` /
`sf32lb52_lcpu_boot.c` / zblue hci_core 的逐行审计结论（file:line 见
代理记录，要点如下）：

### 风暴主源（存在于包括 4.8.46 在内的所有版本）

**楔死期间的故障驱动恢复循环：每 10-16 秒一轮 recover，每轮 2-3 次
LCPU 热复位，无上限。** 机理链：失败 bring-up 的每条 HCI 命令 3s 超时
（0x0c03/0x1001/0x2008…）→ `hci_cmd_timeout_notify` 锁存故障
（recovering==false 时必然）→ 应用下轮 process 命中 10s 闸放行 →
recover()。每次 recover 至少 2 次 `HAL_RCC_Reset_and_Halt_LCPU`
（power_off 停核 + power_on 复位，LB:310/349）+ 每次 power_on 的 RFC
脉冲（LB:179）。热复位只清核不清射频/邮箱域坏状态（`bt ring preboot`
打印旧环索引即证据；实测断电 6.5min 恢复、2min 无效）——**剂量只累积**。

### 4.8.47 升级逻辑的死刑确认（比撤销时知道的更严重）

- `recover()` 入口**无 recovering 重入检查**，且 BR:844 在重启前就清
  `recovering` → 异步 bring-up 窗口内恢复驱动可以再入；
- 失败首启全程 state=OFF（BR:825，零值也是 OFF），故 4.8.47 升级在
  纯 boot 场景惰性（与代码审计一致）；但它若在**有连接会话的 recover**
  中触发（deferred 断连通知把 state 短暂置回 DISCONNECTED，BR:569），
  会对 init_work 仍在 syswq 上运行的 host 再次 `bt_disable_force_mc`
  → hdev 已 free → **UAF / 双重 bring-up / 再叠 2 次热复位**。
  撤销是唯一正确处置。

### 附带发现的 vendor 缺陷（PR 路线清单）

1. `recover()` 入口加 `recovering` 重入防护；`recovering=false` 挪到
   重启完成（或异步 ready）之后；
2. 楔死稳态限流：连续 N 次故障驱动 recover 仍不 ADVERTISING 时，把
   节奏拉长到 ≥60 s（当前 10-16 s 循环是剂量主源）；
3. recover 强拆的 deferred 断连通知竞态：新 bring-up 置 ADVERTISING
   后被迟到的 `bridge_disconnected` 翻回 DISCONNECTED，诱使对健康广播
   做一次 stop/start 往返——需在 recover 后一个窗口内抑制该回调；
4. 过时注释：BR:148/1001 写 "HCI_CMD_TIMEOUT (10s)"，实际已 3s。

### 版本归因方法学的最终提醒

ble.md"最强证据"：同一 bin 连续烧写可 A1 PASS / A2 FAIL——单次烧写
观察对本项目 BLE 行为没有证据力。今后任何"这版好/坏"的结论必须
`ble_adv_lottery.py` 多轮 + 每轮间真断电的 A/B 数据支撑。

## 追加（同日第四轮）：vendor 修复两连败与"打穿机制"的最终认识

4.8.49-ble3（recover 重入防护 + 楔死 60s 限流 + 陈旧断连抑制）与
4.8.50-ble4（撤限流）用户实测均"蓝牙起不来"，彩票 0/8、0/4。复盘后
**全部撤销**（diff 备份 ~/huangshan-logs/ble_bridge_fixes_4.8.49_reverted.patch，
vendor 回到 4.8.46 状态）。

两个机制教训（都有实测数据）：

1. **快速恢复循环就是打穿机制本身**。r7/r8 终态设计：命令超时立即锁存
   （要求 recovering==false）→ 应用毫秒级 recover → 每次 halt+释放
   重新掷一次 LCPU bring-up 骰子 → 数轮内掷中。我加的"recovering 贯穿
   异步初始化"生命周期让超时回调里的锁存被 !recovering 挡住——故障
   锁不进、快打穿死、只剩慢梯子（0/8、0/4）。60s 限流同理是饿死打穿。
2. **恢复节奏的实测边界**：3/8/15s 前倾梯子 0/8；60s 限流 0/8、0/4；
   10s 故障闸 + 15/20/30 梯子（4.8.46 现状）4/6~2/3——**当前节奏就是
   实测过最好的一档，动它之前先留彩票基线**。

recover 重入 UAF（审计确认真实存在）与固定 identity 两个课题移交
vendor PR 路线，前置条件是先解决 deinit 路径健壮性（P1-1 §2.9）。

4.8.51-ble5 = 4.8.48-ble2 的代码 + 新版本号（vendor 全部回到 4.8.46）。

## 追加（11-01 凌晨）：负一屏手势修复与渲染模式结构性调整（未提交，等实测）

用户报告：负一屏近几个版本进不去，右滑被识别为点击。取证与修复（4.8.53-ble7，
工作区未提交）：

1. **触摸探针禁用**（根因之一）：探针是坏屏调试期的标记工具（032577a），
   但 headless 显示用 RENDER_MODE_FULL——**任何失效都全屏重绘 351KB，
   实测一次 ~1.2s**，主循环整个停摆：滑动第一下按下→标记显示→1.2s
   重绘吞掉整个滑动→手势处理器看到的首个按下点已在终点→dx≈0→判定
   为点击。指针包时间戳铁证：11 个包 1.2s 内发送、设备同瞬间才处理。
   已把 `ai_watch_touch_probe_poll` 改为直接返回（代码保留）。
2. **home 的 LV_EVENT_CLICKED 回调移除**：home 屏幕对象上挂着
   `ai_watch_home_click_cb`——滑动结束的 click（固定屏不滚动，滑动
   结束就是 CLICKED）也会推开应用列表。两处"点击进应用列表"（状态机
   tap 分支 + LVGL 点击回调）都按用户要求移除，**应用列表只留上滑**，
   提示文案改为 "Swipe up for apps"。
3. **右滑进负一屏**：home 手势处理原本只有左滑（dx<0）分支，右滑
   落空变点击。现两个横方向都开负一屏。
4. **渲染模式 FULL→DIRECT**（结构性）：缓冲仍是全帧（投屏快照照常），
   但 LVGL 只重绘脏区域——按下高亮/页面切换的 ~100-180ms 全屏重绘
   消失。帧内容已验证有效（195x225、117 色）。
5. **home 手势时长门移除**：分类改纯几何（|dx|/|dy| vs 50px 阈值）。
   远程指针的拖动时长不可控（实测 800ms 真人滑动被 600ms 窗口吞掉）。

**遗留（下会话首要）**：间歇性主循环停摆 ~1.2-1.4s（与触摸无关，
帧请求实测 +1.4s 延迟一次后恢复正常）——它让手势识别仍不稳定
（注入测试 ~1/3 命中）。怀疑方向：光感 I2C 轮询（红线 2，500ms 周期）
或其它周期性阻塞；需要给主循环加 pass 耗时测量定位。
