# 开发日志 2026-10-31b — BLE 不稳调查（连不上 / 授时前 LOST）

固件：**4.8.46-remote**（bin 备份 `~/huangshan-logs/bin_484{3,4,5,6}_remote.bin`）。
前情：同日坏屏投屏链路改造（见本日 a 篇）之后，用户报告蓝牙"容易不好连接上，
容易在授时之前抛 LOST"。

## 用户原始疑问：是不是时序问题？

**是，且指纹与 10-26/10-27 已知的回归家族完全一致**——不是新病，是老病在
投屏时代的显形与叠加。

## 实测抓到的失败形态（主机 hci0 + 串口联合取证）

1. **连接后 ~300 ms 控制器死亡**：`connected` → `controller recovery
   type=hardware-error opcode=0x0000` → `disconnected, reason 0x00
   duration_ms=303` → 强制拆链。与 10-26 日志 §2.2 的"一连上就 Hardware
   error"（采样栈溢出踩堆 → HCPU/LCPU 共享内存 → 控制器崩）同指纹，
   也与 10-27 记录的 r13（~0.5s HW error 0x10）同族。
2. **boot bring-up 彩票**：自研 `tools/ble_adv_lottery.py` 反复上电统计，
   4.8.43 基线 **3/8 boots** 在 12 s 内广播可见；失败 boot 的取证显示
   首次 `bt_enable` 超时（-110）→ 强制拆链 → 重试链。部分 boot 广播
   迟到 10-25 s（+10 s 的 INIT_FAILED 恢复成功路径），部分 45 s 仍暗
   （wedge 深化，P1-1 §2.4：需长断电）。手机早于板子可连就放弃了
   ——这就是"容易不好连接上"的主体。
3. **断开后重广播 -11（EAGAIN）循环**：bridge 只对 -EALREADY 做了清理
   舞步，-11 落进 30 s 退避；后续常被 command-timeout 接力进 recover。

## 排查路上的一次反向教训（重要）

**给 INIT_FAILED 阶梯"前倾"（3/8/15 s 重试）让事情更糟：0/8 boots 在
45 s 内广播**（4.8.44 实测）。`bsp_recover()` 不是轻量探询，是完整控制
器拆链+重建（阻塞主循环 ≤10 s），每跑一次就重置 LCPU-release 竞争时钟；
3 秒一锤等于让竞争窗口永远归零。已回退并改为**温和前倾**（15/20/30/60/
120/300 s），实测 boot 3 的 +10 s 首次恢复在 16.4 s 上线、4.8.46 彩票
4/6（含 24.5 s 迟到案例）。**教训：对这套 fragile bring-up，"更快重试"
不是更强的恢复。**

## 本轮固件改动（全在应用仓，vendor/zblue 未动）

1. `ai_watch_ble.c`：INIT_FAILED 退避温和前倾（首试仍 +10 s，后续
   15/20/30/60/120/300 s），把"暗 boot"的典型恢复时间从 ~40-100 s
   拉到 ~25-45 s。
2. **连接窗口隔离**（10-26 日志的处方，R14 思路的落地）：
   `ai_watch_ble_connect_window_active()` = CONNECTED 且未授时（8 s 硬
   上限）。窗口内主循环：`ai_watch_shot_set_stream_gate(true)` 暂停帧流
   （主机端 1.5 s 超时自动补发，窗口结束自行恢复）+
   `ai_watch_motion_set_slow(true)` 采样降到 15 Hz（4.8.23-p02 验证过
   的安全速率）。窗口结束立即恢复。**掉电/未连接状态不受影响**（预览
   常开）。
3. 未动 TXBUFSIZE=2048。布局位移仍是嫌疑清单第一项（红线 14：ALLSYMS
   实验 46KB 位移曾引发 init wedge 风暴），A/B 方法已备好
   （`ble_adv_lottery.py`），若手机实测仍差再降回 256 对比。

## 追加（同日第三轮）：手机实测反馈与 4.8.47 的撤销

用户实测 4.8.46：首次连接抛一次 LOST → 恢复后能连上；**断开再重连就
永远失败**。投屏守护日志取证：死亡时机后移到连接后 ~4.5-5.3 s（紧跟
CCC 订阅/授时后的首批通知突发）；一次完整成功会话（ccc×2 → time
synced）之后又一起 hardware-error → teardown → 重初始化 → 用户侧再也
连不上（板端最后一行是 advertising as）。

4.8.47 曾试图用"DISCONNECTED>20s 升级 recover + 新鲜链路 2s 静默 +
断开清积压"对症，用户实测"蓝牙根本起不来"后按其要求撤销提交。
**按 ble.md"最强证据"标准，单次烧写的归因没有证据力**——4.8.47 的
app diff 经代码审计在"从未连上的 boot"里是惰性的（DISCONNECTED 分支
进不去），其失败与 4.8.46 一样落在 boot wedge 彩票上。

保留进 4.8.48-ble2 的两项（与 4.8.46 的差异仅此 + 版本号）：
1. **新鲜链路 2 s 静默**：连接后前 2 秒 TX worker 不发通知（首批通知
   突发与 4.5-5.3 s 死亡强相关）；
2. **断开即清空上行积压**：暗期积攒的陈旧遥测不在重连时爆发
   （已知竞态：与 TX worker 阻塞 notify 交错时可能重放一条，影响为
   陈旧数据而非崩溃）。

被撤销的"DISCONNECTED>20s 升级 recover"：recover() 是含 LCPU 热复位
的完整拆链，30 s 一次即是风暴放大器（P1-1 §2.4/§2.6 剂量态）；安全
策略按 4.5.0/4.8.10/4.8.18 三代实测记录 = 事件驱动单次 recover、
teardown 间隔 ≥10-15 s、由 INIT_FAILED 梯子与故障路径承担。

**4.8.48-ble2 用户实测：有提升（2026-10-31 深夜）。** 保留 TX 静默与
积压清理，撤销升级逻辑——与 ble.md"最强证据"标准的教训一致：版本
归因需要多轮 A/B，本轮为单次实测，后续遇到回归先用
`ble_adv_lottery.py`/`ble_connect_test.py` 留多轮数据再下结论。

另证：板子随机地址逐 boot/recover 轮换（62:9C:… → 4E:4B:…）——手机
若按缓存 MAC 重连必败，App 需按名称重扫；根治需 vendor 固定 identity。
