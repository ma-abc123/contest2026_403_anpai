## 1. BLE 栈调研结论

### SiFli BSP BLE 架构

| 层 | 组件 | 配置 |
|---|---|---|
| HCI 传输 | `sf32lb52_bt_adapter.c` → `/dev/ttyHCI0` | `CONFIG_BT_H4=y` |
| BLE 控制器 | LCPU 上的 SiFli BLE 硬件 | 板级初始化 |
| BLE 主机栈 | zblue（Zephyr 移植） | `CONFIG_BT=y` |
| 网络层 | NuttX BT netdev | `CONFIG_DRIVERS_BLUETOOTH=y` |

### 关键发现

1. **zblue 是唯一的 BLE 主机栈**：NuttX 原生 BLE 栈（`nuttx/wireless/bluetooth/Kconfig`）未被构建系统加载，无法通过 defconfig 启用。
2. **zblue API 带 `_mc` 后缀**：`bt_gatt_service_register_mc(dev_id, svc)`、`bt_le_adv_start_mc(dev_id, ...)` 等。
3. **zblue 头文件不可直接包含**：依赖 Zephyr 工具链和 syscall 头文件。
4. **解决方案**：在 SiFli BSP 添加弱钩子 `sf32lb52_bt_register_custom_services()`，AI watch 提供强实现注册 GATT 服务。

### 实现架构

```
sf32lb52_bth4.c (vendor/sifli, 弱钩子)
  └── sf32lb52_bt_initialize()
        ├── uart_bth4_register("/dev/ttyHCI0")
        ├── sf32lb52_bt_zblue_init_once()  ← zblue 初始化
        └── sf32lb52_bt_register_custom_services()  ← 弱钩子调用

ai_watch_ble.c (contest repo, 强实现)
  └── sf32lb52_bt_register_custom_services()  ← 注册 GATT 服务
        ├── 初始化 CCC 结构
        └── bt_gatt_service_register_mc(0, &g_ai_service)
```

### GATT 服务定义

```
Service UUID: 12345678-9abc-def0-1234-56789abcdef0

├── Status Characteristic (f1)
│   ├── Properties: Read + Notify
│   ├── Value: [version(1) + conn_state(1) + last_sync(4)] = 6 bytes
│   └── CCC: 支持通知订阅
│
├── TimeSync Characteristic (f2)
│   ├── Properties: Write
│   ├── Value: [version(1) + utc_seconds(4) + tz_offset(2)] = 7 bytes
│   └── 校验: 长度=7, 版本=1, UTC∈[2020,2100), tz∈[-720,+840]
│
└── DataUpload Characteristic (f3)
    ├── Properties: Notify
    ├── Value: [version(1) + type(1) + payload(N)]
    └── CCC: 支持通知订阅
```

## 6. 风险与已知限制

- **zblue 结构体布局**：本地定义的 `struct zblue_gatt_attr` 必须与 zblue 库的 ABI 完全匹配，否则运行时崩溃。
- **广播时序**：GATT 服务注册在 `z_sys_init()` 之后，但广播可能已由 zblue 自动启动，需要验证服务是否对客户端可见。
- **连接检测**：通过 CCC changed 回调检测订阅状态，但不等于物理连接状态。
- **NuttX 原生 BLE 栈不可用**：`nuttx/wireless/bluetooth/Kconfig` 未被构建系统加载，无法通过 defconfig 启用。
