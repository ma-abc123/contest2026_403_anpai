## 2. 环境最终形态（重要，换机器照抄）

```bash
# ARM 工具链：apt 的 10.3 编不了 LLVM17 libc++，必须官方 14.2
export PATH="$HOME/opt/arm-gnu-toolchain-14.2.rel1-x86_64-arm-none-eabi/bin:$PATH"
export PATH="$HOME/.local/bin:$PATH"        # kconfiglib 三件套

# Python 包（比官方文档多的）：pyelftools cxxfilt devicetree pyyaml
# 串口终端必须带 --omap crlf，否则回车无效：
alias nsh='picocom --omap crlf -b 1000000 --noreset --lower-dtr --lower-rts --logfile ~/huangshan-logs/$(date +%m%d-%H%M).log'
```

其他关键动作：`sudo apt remove -y brltty`（否则 CH340 被抢占不出 ttyUSB）；用户已在 `dialout` 组。

## 4. 踩坑与结论（精华）

### 编译侧
1. **报错要看到最后一行再下结论**。今天三次误判都源于此。
2. GCC 10.3 编不了本分支：vendor libc++ 是 LLVM 17，需要 GCC≥12 的内建 trait → 用 Arm GNU 14.2.Rel1。
3. GCC 14 把 C 历史问题升级成错误：用 `-Wno-error=*` 四件套放行 vendor 老代码（符号链接期都在，只是声明缺失）。
4. `-D_LIBCPP_WORKAROUND_OBJCXX_COMPILER_INTRINSICS` 解决 GCC 内建 trait 与 libc++ 冲突，免改源码。
5. 唯一源码 bug：`frameworks/runtimes/feature/src/utils/feature_utils.h:212` move 构造函数多了 `const`——已修复并提交。

### 板端侧
6. **开机黑屏 ≠ 坏**：Lyra 是 JS 应用，加载要几秒。
7. **`fb` 后全屏淡粉色不是故障**：那是 RGB565 `0xEC1D`（淡粉紫）的第一帧全屏填充，fb 例程只刷一帧；LVGL 连续渲染路径正常。
8. **ostest 卡死在 LPWORK 的元凶是 buttons 例程的僵尸守护进程**（Ready 态占着不干活），kill 掉即恢复正常。KEY2 验证推迟到 M1 自研输入路径。
9. 每次上电 Lyra 自动抢屏：进 NSH 后 `kill -15 8`（PID 以 ps 为准）。

### 认知侧
10. **这个工程有 200+ 嵌套仓库**：`apps/frameworks` 是符号链接；改代码前先 `repo status` 或在文件目录跑 `git status` 确认归属，别在顶层仓库白找。
11. 报错信息里 GCC 建议（如 "did you mean arm_lowputs"）和 exit code 要交叉验证，别只看一行。
12. Ubuntu 22.04 的 brltty 会抢 CH340 串口，装完系统建议直接卸掉。
