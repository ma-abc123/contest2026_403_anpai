## 2. 本轮结论

**BLE"连接崩溃"是 4.9 burst 高频采样引入的回归，非硬件、非手机 App。** 同板同 App 的版本阶梯 [A]：

| 固件 | 采样 | 连接表现 |
|---|---|---|
| **4.8.23-p02**（生产基线） | 15Hz 单字节慢读 | **完美**：connected → CCC=0x0002 → 校时 → 提醒推送；重建版**同样直接能连** |
| 4.9.1-p11a | 27–33Hz burst | 不稳：连→HW error / 连不上 / 连上校时后自己弹开 |
| 4.9.20-r13 | 50Hz burst | 连不上：connected 后 ~0.5s `Hardware error code 0` |

r13 崩溃瞬间判据：`ble pipe cls=NOT-COMMITTED`（TX 环卡命令）+ `alive` 冻结 + LCPU 自报 HW error 事件(0x10) → 控制器被踩死。机理与 `P1-1` §2.2 一致（HCPU 内存被采样踩坏 → 共享 mailbox 坏 → 表现为蓝牙崩）。`lsm6dsl.c` burst 缓冲尺寸本身正确，故更可能是高频采样与连接期服务的**内存/时序竞争**，而非简单越界 [B]。

**9 项 4.9 修复中确有实效但随基线回退（经验留档）：** P0（init 移出 syswq，修 -105 饿屏）、R13（超时归还 `ncmd_sem` 信用，让 R1 resend 真正上线）——它们改善了 **bring-up**，但不解决**连接**回归。

## 5. 后续路线（讨论用）

从 4.8.23-p02 底座做，优先级建议见 `决赛打磨计划`。要点：

1. **50Hz 提速（P1-1/P1-2）是高风险项**：直接上会重演连接崩溃。若要，二选一：(a) 维持 15Hz + 稳 BLE；(b) 设计**连接期采样隔离**（连上则停/降采样，断开恢复）再做 A/B——R14 曾实现（`MOTION_CONN_PERIOD_MS` + `g_motion_conn_throttle`，见备份 patch）但未验证。另可评估 **FIFO+INT1(PA31)** 是否改变 I2C 负载曲线（可能反而更不打扰连接）。
2. **跌倒误报**：P1-1 的窗口按"样本数"定义、50Hz 下时间语义缩短 3.3×。**回到 15Hz 后原标定即适用**——回归验证即可，不必按 50Hz 重标。
3. **手机全链路 + UI/触摸/KEY2 + 计步/活动识别回归**：以 4.8.23-p02 为基线跑一遍确认无回归。
4. 每次改固件 bump 版本号；采样/窗口常量改动须同步 `tools/fall_threshold_analysis.py`。
