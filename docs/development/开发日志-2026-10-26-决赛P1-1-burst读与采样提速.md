## 2. 根因记录

### 2.1 采样率的真实瓶颈分两段：先是 I2C，之后是系统节拍

burst 读把单次读取从 42 ms 压到 1.0 ms 后，实测只有 48 Hz。给采样线程加了
微秒计时才看清：**`usleep` 请求 5 ms / 10 ms，实际都睡 ~19 ms**。原因是
`CONFIG_USEC_PER_TICK=10000`（10 ms 节拍、未开 tickless），一次 10 ms 请求落在
2 个 tick 边界上。读取 1.0 ms + 睡眠 ~18.9 ms ≈ 20 ms → 50 Hz，已到节拍上限。

结论：再提频率不能靠缩短 sleep。抬线程优先级（试验过 120）只多 2 Hz 且会压住
UI/蓝牙，已回退到 80；真正的出路是 **P1-2 档 2**——芯片 FIFO + INT1(PA31)，让
833 Hz 数据先在芯片里排队，一次性 burst 取回，不受 HCPU 节拍约束。

### 2.2 「BLE 一连上就 Hardware error」其实是栈溢出踩坏堆

4.9.0-p11 出现新现象：手机/主机一连上，0.9~3.5 s 内报
`<err> Hardware error, hardware code: 0`，看起来完全像 LCPU 回归。A/B 对照：

| 固件 | 主机「连接→服务发现」结果 |
|---|---|
| 4.8.23-p02（生产） | 稳定，无报错 |
| 4.9.0-p11（环形窗放大，线程栈仍 8 KB） | 连接后 914 ms Hardware error，断连 |
| 4.9.1-p11a（栈 8 KB→16 KB） | 连接 + 服务发现全程稳定 |

机理：本项目的 DSP 环形窗（`dev_ring`/`dev_ring_ms`/`act_ring`）是**采样线程栈上的
局部数组**。按 ~60 Hz 重算后从 34/34/68 增到 64/64/128，栈用量 +480 B，再加周期
统计日志，8 KB 栈越界写坏堆；HCPU 与 LCPU 共享内存，于是以「蓝牙控制器崩溃」的
形式暴露。教训：**看到 BLE 异常，先量本次改动有没有增加栈/堆占用，别先怀疑蓝牙。**

同类外溢还查出一处真实越界：0x12 运动帧 `uint8_t payload[14]` 却 `memcpy` 了 12 字节
（偏移 4 起写到 16），编译器 `-Warray-bounds` 报出。按现有 14 字节帧长改为只拷 5 个轴
（串口 CSV 仍记全部六轴），协议长度与手机端解析的偏差单列到 2.5。

### 2.3 NuttX `i2c_writeread()` 与 SiFli I2C 下半层不兼容

第一版 burst 用 `i2c_writeread()`，上板后采样率反而掉到 ~0.8 Hz。日志与代码对齐后定位：
`i2c_writeread()` 只给第一条消息打 `I2C_M_NOSTOP`，第二条是裸 `I2C_M_READ`；而
`vendor/sifli/chips/sf32lb52/sifli_i2c.c` 的 transfer 解析**只在第二条带
`I2C_M_NOSTART` 时**才走 `i2c_mem_ops()` 组合事务，否则把 NOSTOP 那条直接丢弃、只发一条
普通读。结果寄存器地址从未写出去，读的是传感器「当前地址指针」处的随机寄存器——
STATUS_REG 判据因此几乎永远不成立（327 次循环仅 8 次成功）。

改法：驱动内手工组两条消息（`I2C_M_NOSTOP` 写地址 + `I2C_M_NOSTART|I2C_M_READ` 读块），
读成功率回到 100%（`ok=500 eagain=0 loops=500`）。这也是可上游化的通用教训：块读要走
真正的 repeated start，而不是「写地址带 STOP」的两段事务。

### 2.4 LCPU 楔死只有真正断电才解得开，且「断电」要够久

`sf32lb52_lcpu_boot.c` 的 `lcpu_power_off()` 实际只做 `HAL_RCC_Reset_and_Halt_LCPU(0)`，
`lcpu_power_on()` 是唤醒 + 核复位 + 重下补丁——**复位的是核，不是射频/邮箱域**。日志佐证：
`bt ring preboot: size=… rd=… wr=…` 打印的正是热复位后仍保留的旧环索引，
`sf32lb52_bt_prepare_lcpu_boot()` 还要显式清零。加上 E1 补丁当初就是**特意去掉 RFC 复位脉冲**
（HW error 剂量效应的修复），软件里已无任何路径能碰那个域。

因此一旦射频域进入坏状态，唯一的复位手段是真的掉电。而 BT 电源经 PMU/LDO 有大电容，
拔线几秒等价于又一次热复位。本轮实测：**拔电约 6.5 分钟→恢复；拔电约 2 分钟→照旧失败**
（样本还少，暂按「需 5 分钟以上」处理，待复现）。

软件侧还有两个放大器（均未改，属已关闭的 BLE 线）：
1. 恢复落到 syswq 线程时，`external/zblue/zblue/port/lib/net_buf/buf.c:306` 会把超时
   强制改成 `K_NO_WAIT`（日志 `Timeout discarded. No blocking in syswq`），于是每次
   `bt_enable` 秒失败 `-105`；
2. 应用侧 `ai_watch_ble.c` 的 INIT_FAILED 自动恢复上限 5 次，跑满后**不再广播**，
   手机侧表现为「彻底连不上」，只能重启/断电。

### 2.5 蓝牙重试风暴会饿死采样线程（跌倒检测风险，待 P1-2 解）

BT 反复 `bt_enable` 期间，prio 80 的采样线程睡眠被拖到最长 **1.1 s**，实测采样率
掉到 43 Hz、最低 37 Hz。也就是说一次蓝牙异常可能让跌倒算法出现 1 秒的采样空洞。
本任务先用日志把这个现象钉住，解决路径仍是 P1-2 的 FIFO + INT1（芯片侧缓冲）。

### 2.6 「不拔电就救不回来的 wedge」实验线（进行中，结论未定）

电池供电与答辩现场无法拔电，故对 wedge 恢复做了第一轮实验。三条事实：

1. **boot 路径本来就在脉冲 RFC**：`bt_rf_cal()`（每次 `lcpu_power_on()` 都跑）内部
   调用 `HAL_RCC_ResetBluetoothRF()`（`bt_rf_fulcal.c:5380` → 拉 `RSTR1.RFC`）。
   E1 移除的是 LCPU 补丁里**连接路径**上的那次脉冲。所以「boot 期 RFC 脉冲」在
   生产版一直存在且仍能 0 HW error，不能把我加的脉冲当成 HW error 主因。
2. **r4 的「MAC 时钟被门控」假说没有 HCPU 侧抓手**：全树 grep 证实 BT bring-up /
   teardown 中没有任何 `HAL_RCC_EnableModule/DisableModule` 调用
   （`RCC_MOD_MAC/PHY/RFC` 从未被 HCPU 门控），门控只可能发生在闭源 ROM 内部，
   与 r6-r8「host 侧无修复路径」的结论一致。
3. **可上游化的 vendor 缺陷**：`HAL_RCC_ResetModule(RCC_MOD_MAC/PHY/RFC)` 在
   SF32LB52X 上必然 `HAL_ASSERT(0)`（其 LPSYS group-1 分支被 `#ifndef SF32LB52X`
   排除），且它把 **ENR**（时钟使能）寄存器掩码当成 **RSTR** 复位位使用。
   任何依赖它做模块复位的 52x 代码都是静默失效的。

实验与结论（暂定）：

| 变体 | 改动 | 现象 |
|---|---|---|
| 4.9.6-p11g | 无块复位 | 热复位后 `-110` 连打 4~8 次→`-105`，试满 5 次后**永久不广播** |
| 4.9.7-p11h | MAC+RFC 块复位 | 楔死态烧录后 1 次重试即恢复广播，主机连接+订阅正常 |
| 4.9.8-p11i | MAC+RFC + 无限重试 | 开机 5 次重试恢复；压力第 1 轮连接+发现 8 特征值正常，随后 1 次 HW error → 再楔死，10 次失败/4 分钟不自愈 |

第 3 行说明 **MAC+RFC 脉冲不是可靠解**，且我叠加的 RFC 脉冲与已知剂量效应同源，
应当去掉。已收敛为 **4.9.9-p11j：只脉冲 `RSTR1.MAC`，不碰 RFC**（`bt_rf_cal` 已在
同一 boot 里做 RFC），并保留「INIT_FAILED 无限耐心重试」这一项纯改善
（旧 5 次上限会让手表在电池供电下永久失联）。

**待做的判定实验**：彻底断电 5~10 分钟清掉今日的反复热复位剂量态后，用同一套主机
压力协议（8 轮「连接→服务发现→断开」）分别跑 p11j 与生产版 4.8.23-p02，统计
HW error 次数 / wedge 次数 / 自愈重试次数与用时，才能给这两项改动定性。


### 2.7 LCPU 的 Command Complete 是 `ncmd` 在前：分析侧「每条命令都被 reject」是解码序造成的假象

反汇编侧（`handoff_to_dev_r10`）七轮 483 份快照的结论是「1213 条 CC 全部 `status=0x06 /
credits=0`，第一条还回显 host 从未发过的 0xFC11」，并据此要我们做「失配快速失败」（P1(2)）
和「擦 LPS RAM 清锁存的 reject 上下文」（P2）。**实测把这个前提打掉了。**

- 源码侧：`external/zblue/zblue/include/zephyr/bluetooth/hci_types.h:2948` 的
  `struct bt_hci_evt_cmd_complete { uint8_t ncmd; uint16_t opcode; }` **只有 3 字节、ncmd 在前**；
  status 由 `struct bt_hci_evt_cc_status` 追加在后面（`subsys/bluetooth/host/hci_common.c:28`
  的构帧函数 + `subsys/bluetooth/controller/hci/hci.c:323` 的调用方）。读侧
  `hci_core.c:2711` 与之一致：吃掉 3 字节后用 `status = buf->data[0]` 取第 4 个字节。
  ⇒ zblue 生态里 CC 的参数序是 `[ncmd][opcode LE][status][返回参数]`。
- 实测侧（x3/x4 适配器投递打印 + host 解析逐条对照）：

  ```
  bt rx raw: len=7  04 0e 04 06 03 0c 00      →  CC opcode=0x0c03 status=0x00 credits=6
  bt rx raw: len=13 04 0e 0a 06 09 10 00 12   →  CC opcode=0x1009 status=0x00 credits=6
                          紧接 "Identity: CD:AB:78:56:34:12"（地址最低字节 0x12 就在参数第 4 个）
  ```

  按规范序 `0x06` 是 status（未知命令），可**出错回复不会带回完整参数**：`0x1009`
  的 plen=10 = 4 字节头 + 6 字节 BD_ADDR，是实打实的成功回复。
  另外 `p[0]` 只在 6 与 1 之间按命令类别变化（信用数才会这样，状态码不会），
  且「所有命令都 reject 的控制器不可能广播+连接+跑 GATT」——这三条一起才是判据。
- ⚠ 方法论：两种序下**返回参数的起始位置是同一个字节**，所以「某字段解得对不对」不能当判据
  （我们第一稿就是这么论证的，作废）。
- 顺带：Command **Status**（事件 0x0F）用的是规范序（`{status; ncmd; opcode}`），
  所以 `CS opcode=0x0801 status=0x01` 那 13 次「答非所问」是真的，与 CC 序无关；
  可疑形状是 `0x2008→0x0801 / 0x2009→0x0901`（opcode 高位被吃掉），与 0xFC11 可能同源。

⇒ **wedge 的真实形状因此被重新刻画**：HCI_Reset 通常是被正常回答的，
死的是它后面第一条命令（x4 的 8 次超时里 7 次是 `0x1003`）。P1(2)/P2 失去靶子，P0 保留。

### 2.8 恢复路径确实跑在 syswq 上（分析侧 P0 成立，我们此前怀疑错了）

x1 那次 panic 的任务表 + 两处探针给出三重独立证据：

```
dump_task:   5   0 110 FIFO pthread … sysworkq              ← PID 5 就是 syswq，优先级 110
dev:0: Sending HCI_RESET tid=5                               ×19（hci_core.c common_init 第一句）
<wrn> Timeout discarded. No blocking in syswq (pool 0x2000bad4 tid=5)   ×9（守卫按定义只在 syswq 打印）
```

`ai_watch_ble_process()` 本身在应用主任务（PID 7）里跑、bridge 里没有 `k_work_submit`，
但 `bt_enable()` 往下的 init 序列落在 syswq（`CONFIG_BT_RECV_WORKQ_SYS=y`）⇒
`port/lib/net_buf/buf.c` 的「不许在 syswq 阻塞」守卫会把每条 init 命令的分配超时改成
`K_NO_WAIT`。x2 的 19 次恢复里 **9 次是 `-105`**，且这 9 次**没有一行 `cal:`/`ring preboot:`**
——一次都没重新引导 LCPU，纯空转。下一轮按变体 A 把恢复挪到独立 work queue（优先级 90）。

### 2.9 构建 X（300 ms 超时 + 失配快速失败）实测：误伤 4 次 + 全场唯一一次硬故障

- 快速失败 4 次全部打在 Command Status 上（`0x0801↔0x2008`、`0x0901↔0x2009`），
  把「还能等」变成 `advertising start failed: -5`，其中 2 次紧跟着 `Hardware error`。
- 超时降到 300 ms 后恢复频率 ×10，撞进
  `bt_disable_internal → h4_close → sf32lb52_bt_controller_deinit → lcpu_power_off →
  HAL_RCC_Reset_and_Halt_LCPU`，在 `arm_doirq` 上下文里 `arm_hardfault.c:186` panic
  （整场 20 MB 日志唯一一次）。x2/x3/x4/x5 回退后 0 次 panic。
⇒ 任何「更快重试」的设计必须先解决这条 deinit 路径的健壮性，否则恢复阶梯会变成硬故障。

### 2.10 P4「bring-up 期停 motion」必须带截止时间，否则跌倒检测无限期失明

x1 最差 `MOTION: rate 1 Hz`；x2 整个观测窗口**一条 rate 行都没有**（BLE 从未进 ADVERTISING，
而暂停只在到达 ADVERTISING/CONNECTED/DISCONNECTED 时解除）。作品的核心功能被 BLE 拖死，
这是不可接受的耦合。修法：所有暂停点统一走 `ai_watch_ble_motion_pause()`
（`ai_watch_ble.c:716`），暂停即挂 20 s 截止时间，每次恢复尝试重新计时，到点无条件恢复。
x4/x5 实测：暂停期 10/19/44 Hz → 解除后立刻 `rate 50 Hz ok=500/500`，链路恢复不再影响采样。

### 2.11 回归红灯：连接建立期 `Hardware error` 在 x4 复现（p02 未复现）

x4 两次连接 2 次 HW error（3644 ms / 973 ms），同板同手机同时间段的 4.8.23-p02 是 1 连接 0 次。
已排除两个假因：E1 blob 仍在（`g_lcpu_patch_bin[]` 小端展开 SHA256 = `85e2028f4069…73b472a9`，
与 r7 指纹一致）；motion 线程栈已是 16304（不是 2.2 的病灶）。
剩下两个 p02 之后引入的剂量变量：① 采样 15→50 Hz（连接窗口 I2C/CPU ×3）；
② p11h 起 `lcpu_power_on()` 里我们自加的 `RSTR1.MAC` 脉冲（从未证明对 wedge 有益，
而复位脉冲正是连接路径 HW error 的已知剂量来源）。
**x5 = x4 − ②**（删掉 `sf32lb52_lcpu_ble_block_reset()` 与调用）已在板上跑；
若仍必现则做 x6（`MOTION_PERIOD_MS` 10→66，回到 15 Hz）单验 ①。
这条是 P1-1 能否进决赛版本的闸门：不能拿连接稳定性换采样率。

## 3. 与采样率配套的参数重算（红线 #5：脚本必须与固件同源）

窗口参数原本按 ~15 Hz 定为样本数，提速后必须按时间等价重算，否则静止判定只覆盖
0.5 s、活动窗被拉长：

| 参数 | 15 Hz 原值 | 50 Hz 新值 | 时间含义 |
|---|---|---|---|
| `DEV_RING_LEN` | 34 | 64 | ≥1 s（实际游走受 `DEV_RING_MS` 时间约束） |
| `ACT_RING_LEN` | 68 | 100 | 2 s |
| `ACT_DEBOUNCE_SAMPLES` | 40 | 50 | ~1 s |
| `activity_confident` 门限 | 100 样本 | 300 样本 | ~6 s |
| `BLE_REC_DEC` | 4（15 Hz→3.8 帧/s） | 12（50 Hz→4.2 帧/s） | 保持 ~4 帧/s（indicate ~120 ms/次的上限） |
| 线程栈 | 8 192 | 16 384 | 见 2.2 |

离线脚本 `tools/fall_threshold_analysis.py` 的 dev ring 上限同步 40→64 与固件对齐。
**已在旧 15 Hz 测试集上验证该改动是中性的**：cap40 与 cap64 两版输出逐字一致，
两组跌倒仍复现记录值（3936 mg/81°、2185 mg/31°），走路/静止/甩动 0 误报。
