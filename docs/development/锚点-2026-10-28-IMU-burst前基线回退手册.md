同一天、同一时刻、7 个仓库的一次性快照。任何一个仓库单独回退都可能造成不一致，所以脚本是整组操作的。

| `nuttx` | `569884fa6e9` | 内核与驱动（IMU burst 读要改这里） |
| `external` | `6eb5699` | zblue 的 CMake 包装层 |

| `vendor/sifli` | `e0c069e` | 厂商 HAL + **E1 LCPU 补丁**（本次新提交） |
| `frameworks/runtimes/feature` | `a87e85df` | 运行时特性 |
| `vendor/openvela` | `f352617` | 上游基线（板级软链挂在这里） |

> 注意 `external` 和 `external/zblue/zblue` 是**两个独立仓库**，不是父子关系。只回退前者不会回退 zblue。

> **为什么 contest 那一行不写死 commit**：回退脚本 `tools/revert-to-baseline.sh`
> 自己就住在 contest 仓库里。如果锚点指向"脚本被提交之前"的那个 commit，
> 那么执行回退会把脚本本身删掉 —— 下次就没工具可用了（自举问题）。
> 所以 contest 的锚点必须包含脚本本体，tag 也必须在脚本提交之后才落。
> 查实际 commit 用：`git -C contest2026_403_anpai rev-parse 'pre-imu-burst-20261028^{commit}'`。
> （**注意必须带 `^{commit}`**：这是 annotated tag，裸 `rev-parse <tag>` 返回的是
> tag 对象自身的 SHA，不是它指向的提交，两者不同。）

## §2 本次提交了什么：E1 LCPU 补丁

commit `e0c069e`（`vendor/sifli`，本地，**未推送**）。

### 它改的是什么

`middleware/bluetooth/patch/sf32lb52/sf32lb52_lcpu_patch_exp.h` 里的
`g_lcpu_patch_bin[]`，把第 `[1164..1171]` 共 8 个 word（16 条 Thumb 指令）
替换成 `0xBF00BF00`（16 条 `NOP`）。

被 NOP 掉的原指令，反汇编如下（这是**根因**，值得记住）：

```asm
mov.w  r6, #0x40000000     ; RFC 控制寄存器基址
ldr    r0, [r6]
orr.w  r0, r0, #0x40000    ; 拉高 bit18
str    r0, [r6]            ; ─┐
movs   r0, #5              ;  │ 一次完整的
bl     <delay>             ;  │ RFC 复位脉冲
ldr    r0, [r6]            ;  │
bic.w  r0, r0, #0x40000    ;  │ 拉低
str    r0, [r6]            ; ─┘
movs   r0, #5
bl     <delay>
```

即：厂商 blob 在 **BLE 连接路径**上会复位一次射频控制器。revid=3 的硅片上，
这一次复位直接导致连接后 1–2 秒内 `Hardware error code 0`。NOP 掉它之后
崩溃率从 78% 降到 0/4。

### 校验结论（已逐字比对，不是抽样）

- `g_lcpu_patch_list[]`：62 个 word，与厂商 blob **完全相同**，未改。
- `g_lcpu_patch_bin[]`：2040 个 word（8160 B），**恰好 8 个 word 不同**，全部是 `0xBF00BF00`。
- 其余 2032 个 word 与厂商 blob 逐字相同（含那些 `0x2040xxxx` 的地址常量）。
- 数组总长未变，仍 8160 B < `LCPU_PATCH_TOTAL_SIZE`（8 KiB）。
- 文件里其余改动只是排版（每行 4 值 → 8 值、大写 → 小写），数值语义不变。

### 为什么本地保留不推送

厂商闭源补丁，按《决赛打磨计划》P0-C 不走 PR。它是本地构建能连上蓝牙的**前提**，
一旦丢失，`revid=3` 会回到"每次连接必崩"。所以这次必须入库 —— 放在工作区里
迟早会被某次 `checkout`/`sync` 抹掉。

## §4 五条硬约束（违反会出事）

1. **绝不用 `git stash -u` / `git clean -fd` 做回退。**
   `vendor/openvela/boards/contest2026_403_ai_watch` 是**未跟踪的软链**，构建靠它。
   被收进 stash 或删掉后，`ninja` 会报一个与源码毫无关系的错，极难定位。
   `git reset --hard` 本身不删未跟踪文件，所以"只 reset、不 clean"是安全的。

2. **回退后必须重建，不能只回退就烧。**
   `cmake_out/prod` 是产物，不受 git 管。源码回退了、产物还是改坏那版，
   烧进去会得到"明明回退了却还是坏的"的假象。

3. **tag 不会随 `git push` 自动走。**
   哪天要换机器或在 clone 上回退，需要显式 `git push origin pre-imu-burst-20261028`
   （本项目当前策略是不推送，所以这个 tag 只存在于本机）。

4. **`vendor/sifli` 含 `logs:` 提交的分支严禁推到 fork / 公共仓。**
   2026-09-09 曾因误推导致 checkpatch 失败。本次提交是 `fix(sf32lb52):`，不涉及。

5. **不要在 `packages/`、`vendor/openvela/` 下直接编辑或提交。**
   它们是软链映射，真正的源在 `contest2026_403_anpai/`。

## §5 三步开发路线与检查点

已确定的顺序：**IMU burst 读 → 光感 → 50Hz 测试**。这个顺序不是随便排的，
三步之间存在硬依赖：

```
burst 读  ──→ 总线占用 168% 降到个位数 ──→ 光感才抢不到 IMU 的时间片
                                        └→ 50Hz 才不会重演 4.9 的连接崩溃
```

**50Hz 放在最后是唯一正确的顺序。** 4.9 版就是跳过前两步直接上 50Hz，
结果总线彻底堵死、BLE 连接崩掉，最后被迫整体回退到 4.8.23-p02。
如果顺序反了，同一个坑会再踩一次，而且这次会误以为是"光感导致的"。

### 第 1 步：IMU burst 读（P1-1）

- **改哪里**：`nuttx/drivers/sensors/lsm6dsl.c`（把 17 次 `readreg8` 合成 1 次连读），
  可能涉及 `ai_watch_motion.c` 的调用方式。
- **预期收益**：加锁次数 34 → 2，总线占用 168% → 个位数。
- **验收**：`/dev/lsm6dsl0` 六轴数据与改前一致（同一姿态下 ±噪声内）；
  motion 线程周期实测回到 25ms 附近；BLE 连接、CCC、timesync 与改前无差别。
- **坏了怎么办**：`git -C nuttx reset --hard pre-imu-burst-20261028`，重建。
- **注意**：这是唯一一步**不改内存布局**的改动，也因此是三步里风险最低的。
  4.9 的教训就是碰了内存布局（LCPU mailbox 窗口），这次不碰。

### 第 2 步：光感 LTR-303ALS-01

- **前置**：第 1 步验收通过。总线有余量之后再做。
- **先做档 1「点灯验证」**：起线程读 `0x29` 的 Part ID（寄存器 `0x86`，应为 `0x86` 值），
  只 `printf`，不接业务。读到再往下走，读不到整条线砍掉，零损失。
- **要加应用层 mutex**：I2C 的锁是**每次 transfer** 粒度，`readreg8` 之间是开放的。
  只包单次 transfer 等于没加，必须包住整个 `sensor_read()` 调用。
- **验收**：IMU 采样周期无可测退化；lux 读数随遮光/手电筒单调变化。
- **坏了怎么办**：同第 1 步，但注意光感若新增了 nuttx 驱动文件，
  未跟踪文件不会被 reset 删除，需要手工清掉（**只删你自己新建的文件**）。

### 第 3 步：50Hz 采样

- **前置**：第 1、2 步都验收通过。
- **为什么能做了**：此时总线占用是个位数，50Hz（周期 20ms）不再是超载；
  若没做第 1 步，50Hz 必然重演 4.9。
- **验收**（"功能性完全正常"要拆成可判定项）：
  1. BLE 连续连接 ≥ 6 轮不掉线（当前基线只有 1 轮证据，这本身就是待补项）；
  2. 跌倒检测：`tools/fall_threshold_analysis.py` 的离线定标集跑一遍，阈值不需重调；
  3. 计步：走 100 步，误差在可接受范围；
  4. 抬腕/息屏：无误触发；
  5. 无 `Hardware error code 0`、无 wedge、无 panic。
- **坏了怎么办**：先单独把 `MOTION_PERIOD_MS` 退回 25，确认问题是否只由频率引起；
  若仍坏，整组回退锚点。
