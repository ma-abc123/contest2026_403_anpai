## 1. 审计结论(为什么重写)

### 1.1 构建链路断裂(最关键)

| 检查点 | 结果 |
|---|---|
| 旧 `nuttx` ELF 中 zblue 符号 | **0 个**(`z_sys_init`/`bt_enable`/`bt_gatt_*` 全部缺失) |

| `libzblue.a` | 已编译但从未被链接 |

### 1.2 旧 `ai_watch_ble.c` 不可用(死代码 + ABI 猜测)

1. 手写 `struct zblue_gatt_attr`/`zblue_gatt_service`/`zblue_gatt_ccc` 等 ABI 结构、extern 猜测签名 —— 违反 zblue 集成约束,已全部删除。

3. "强实现" `sf32lb52_bt_register_custom_services()` **不注册任何服务**,只打印日志并置状态;`g_ai_service` 属性表从未被使用。
4. 开发日志声称的 BSP 弱钩子在 vendor 树中不存在(grep `custom_services` 为空)。
5. `ai_watch_ble_init()` 把状态一次性拷给应用,之后永不更新;应用轮询的状态是假的。

|---|---|

## 3. 协议(与交接要求一致,已在代码中固定)

```
Service     12345678-9abc-def0-1234-56789abcdef0
Status   f1 12345678-9abc-def0-1234-56789abcdef1  Read+Notify  [version(1)][conn_state(1)][last_sync(4)]
TimeSync f2 12345678-9abc-def0-1234-56789abcdef2  Write        [version(1)][utc(4)][tz_offset_minutes(2)]
DataUpload f3 12345678-9abc-def0-1234-56789abcdef3 Notify      [version(1)][sensor_type(1)][payload(N)]
Command  f4 12345678-9abc-def0-1234-56789abcdef4  Write        [version(1)][cmd_type(1)][id(1)][flags(1)][timestamp(4)][title_len(1)][title(N)]
```
- 所有多字节字段小端;UUID 由 `BT_UUID_128_ENCODE` 正确编码。
- TimeSync 校验:版本=1;UTC ∈ [1577836800, 4102444800](2020-01-01 ~ 2100-01-01);tz ∈ [-720, +840];非法输入返回 ATT 错误码,不崩溃。
- RTC 恒存 UTC;时区仅用于 UI 显示(`gmtime_r(utc + tz*60)`),不会重复叠加。

## 8. 附录:实机首验崩溃记录与修复(2026-08-28 晚)

**现象**:烧录后屏幕不亮,串口在 `KEY2 button monitor started` 之后硬故障:

```
arm_hardfault ← bt_conn_cb_register_mc+0x25 ← ai_watch_ble_bsp_start+0x15 ← ai_watch_main
```

**根因**:本 zblue 移植的 `bt_conn_cb_register_mc()` 会解引用 `hdev->conn_ctx`(conn.c:2895 起),而 `conn_ctx` 只在 `bt_enable → bt_init → bt_conn_init`(conn.c:4491)时才分配。我在 `ai_watch_ble_bsp_start()` 里、`bt_enable()` 之前调用了注册,conn_ctx 为 NULL → 硬故障。UI 创建完成但主循环未进入,所以屏幕不亮。

**修复**:连接回调注册移入 `bridge_bt_ready()`(bt_enable 完成回调内,此时 conn_ctx 已就绪);`ai_watch_ble_bsp_start()` 只保留 `bt_enable()` 调用。

**验证**:重建通过(nuttx.bin 7,899,980 B / 22:24),重新烧录后按第 5 节步骤验收。

### 8.1 第二轮:bt_enable 失败 (-EIO),HCI_RESET 发送被拒(err -22)

**现象**(烧录 22:24 固件):屏幕点亮、触控就绪,但:

```
dev:0: Sending HCI_RESET
<err> Unable to send to driver (err -22)
<wrn> opcode 0x0c03  status 0x1f
aiwatch-ble: bt_enable failed: -5
```

**分析**:
- `-22` 是 zblue h4 驱动的**掩蔽值**(`h4_send` 里 write 返回值 ≠ 长度一律转成 -EINVAL),真实 errno 被吞。
- 代码排查:`sf32lb52_bt_send` → `emulate_cmd(0x0c03)` 不模拟 → `ensure_controller_enabled`(已有日志,未出现=未失败)→ `controller_enable`(失败路径部分静默)→ `host_send_packet`(-ENODEV 分支静默)。所有已见日志的路径都没触发,唯一完全静默返回 -EINVAL 的位置是 `uart_bth4_write` 的 H4 类型字节解析分支。
- 结论:无法从代码推演定位,需仪器化。

**处置**:给发送链所有静默失败点加日志(bth4.c `sf32lb52_bt_send` 入口/模拟失败/host_send_packet 失败、`sf32lb52_bt_open` 各步、bt_adapter.c `controller_enable` 的 status 检查/`ipc_queue_open`/`lcpu_power_on`、`host_send_packet` 的 controller-not-ready 检查)。失败日志只在出错时输出,保留为长期诊断能力。

**等待实机重测**(nuttx.bin 22:47)。判定表:
| 下一轮日志特征 | 指向 |
|---|---|
| 无 `bth4 send: cmd opcode=0x0c03` 行 | 失败在 uart_bth4_write 内(类型字节/重组),需查 core |
| 有 send 行 + `controller enable failed: -EPERM` | status 状态机问题(open 未执行) |
| 有 send 行 + `ipc_queue_open failed` | IPC 队列初始化/邮箱使能问题 |
| 有 send 行 + `rx ring not ready` | LCPU 固件未起/IPC 环未就绪 |
| 有 send 行 + `host_send_packet failed: -ENODEV` | enable 与 send 状态不一致 |
| 有 send 行 + 无错误但后续仍失败 | RX 方向问题(LCPU→HCPU 事件未到达) |

### 8.2 第三轮:失败点收窄到写入层入口

**22:47 固件实机结果**:有 `opening HCI controller`/`open ok`,仍无 `bth4 send:` 行 → `sf32lb52_bt_send` 未被调用,失败在更上游。

**新发现**:
1. port 的 `zephyr/logging/log.h`(apps/external/zblue/zblue/port/include)按 syslog 优先级编译日志:DBG=7、INFO=6、WRN=4、ERR=3,受 `CONFIG_BT_DEBUG_LOG_LEVEL=6` 控制 → **LOG_DBG 全部不编译**,INF/ERR 在。之前"h4 驱动日志死掉"的判断修正为:只有 DBG 级不可见。
2. h4.c 的 `LOG_LEVEL CONFIG_BT_HCI_DRIVER_LOG_LEVEL`(不存在的 Kconfig)已在 23:08 固件回退为全局级别(仅影响 DBG 可见性)。

### 8.3 第四轮:定位到 write 系统调用层,write 根本未进入 uart_bth4 驱动

**23:24 固件实机结果**(关键行):

```
sf32lb52 bth4: opening HCI controller     ← bt_open 成功(uart_bth4 的 open 已通)
sf32lb52 bth4: HCI controller open ok
h4: opened /dev/ttyHCI0 as fd 5           ← open 成功
dev:0: Sending HCI_RESET
h4: write failed fd=5 ret=-1 nwritten=0 count=4
```

- `uart_bth4: write buflen=...` 入口日志**未出现**,`sendlock failed` 也未出现 → `uart_bth4_write` 未被执行;write 失败发生在 VFS 层。
- `ret=-1` 是 libc write() 包装的返回(实际错误码在 errno);h4.c 把任何非 EAGAIN 错误规范化为 -EINVAL,hci_core 再报 -22,真实 errno 被双重掩蔽。
- 已核实:`k_thread_create`/`k_work_queue_start` 在 port 中用 pthread(同任务组,共享 fd 表),open 与 write 理论上同表;无第二个 /dev/ttyHCI0 注册者(bt_driver_register/bt_uart_register 在本板无调用方)。
- 悬而未决:fd 5 在 write 时是否仍有效、真实 errno 是什么。

**23:41 固件新增**:h4 write 失败时打印 `errno` 与 `fcntl(fd, F_GETFD)`(fd 有效性)。

**判定**:errno=9(EBADF)→ fd 在 write 前被关闭/替换,追查关闭者;errno=1/13/22 → 驱动层拒绝,查 inode 绑定;errno=11(EAGAIN)→ 阻塞标志问题;errno 数值异常 → 怀疑 BT RX WQ 线程栈溢出(CONFIG_BT_RX_STACK_SIZE=1200 偏小,需加大并重试)。

### 8.4 第五轮:根因确认 —— NuttX fd 按任务组隔离,zblue sysworkq 线程不可见应用组的 fd

**23:41 固件实机结果**:

```
h4: opened /dev/ttyHCI0 as fd 6
dev:0: Sending HCI_RESET
h4: write failed fd=6 ret=-1 errno=9 F_GETFD=-1 nwritten=0 count=4
```

**errno=9(EBADF),F_GETFD=-1** —— fd 6 在 write 时无效。根因链:

1. zblue port 的 `k_sys_work_q`("sysworkq")由 `SYS_INIT(k_sys_work_q_init, POST_KERNEL)` 启动 → 运行在 `z_sys_init()` 所在任务组(board_late_initialize,init 任务);
2. 本板应用(ai_watch_main,pid 7)是独立任务(独立 fd 表);`bt_enable` 在应用任务里 `open("/dev/ttyHCI0")` → fd 只存在于应用组;
3. `bt_enable(cb)` 把 `hdev->init`(= bt_init/hci_init,含全部 HCI 命令发送)经 `k_work_submit` → sysworkq(另一个任务组)执行 → 该组看不到 fd 6 → **EBADF**;
4. h4.c 把任何失败规范化为 -EINVAL → hci_core 报 -22 → bt_enable -EIO。前三轮所有矛盾日志由此完全解释。

**修复**(zblue port h4.c,根因级):写路径改用 NuttX `struct file` API(`file_open/file_write/file_close`)——struct file 是组无关的内核句柄,任何任务组可用;fd 仅保留给 RX 线程(它运行在调用 bt_enable 的应用组)做 poll/read。附带修复:`file_write` 直接返回负 errno,原来永远不生效的 `-EAGAIN` 重试逻辑恢复工作。

**验证**:重建通过(nuttx.bin 7,900,352 B / 00:00)。预期下一轮:HCI_RESET 到达 SiFli 驱动(`bth4 send: cmd opcode=0x0c03`)→ controller_enable(LCPU 上电、IPC 打开、rx ring 就绪)→ 控制器响应 → bt_init 完成 → `ready, GATT service exposed` → 广播。若 LCPU 固件/校准有问题,会看到 `rx ring not ready: -110`。

### 8.5 第六轮:BLE 全链路打通 ✅;新问题:连接后触屏冻结(待查)

**00:10 清理版固件实测**:手机 nRF Connect 成功扫描并**连接**手表 —— 阶段 1 的 BLE 带外链路(栈初始化→LCPU 控制器→HCI→广播→连接)全通。fd 修复经受住了实机检验。

**新问题**:连接后触屏无响应,无法进入应用列表页。

**初步分析**(未改动代码):
1. 排除"等手机发时间":应用对手机数据是轮询消费,永不阻塞等待。
2. 触屏依赖应用主循环(LVGL timer handler 读 /dev/input0)。无响应 = 主循环被饿死或阻塞。
3. **首要嫌疑:BT 线程优先级压制应用**。`CONFIG_BT_RX_PRIO=8`,port 将 Zephyr 协作优先级直接映射为 NuttX 高优先级(此前 dump 中 "BT LW WQ" prio=10 vs 应用=100)。空闲时 BT 线程阻塞在信号量上(故连接前正常);连接瞬间 nRF Connect 自动 MTU 交换/GATT 发现/读特征/订阅 CCC 产生持续事件流,高优先级 BT 线程若自旋不让出 CPU,应用(prio 100)被饿死 → LVGL 停摆。
4. 次要嫌疑:某 GATT 发现路径死锁/死循环,吊住高优先级线程。

### 8.6 第七轮:连接成功但"上电直连后首次点按"硬故障 → 定位为 zblue 缓冲池配置不足

**实机日志关键信息**:
- BLE 全链路真实验证通过:`Identity: CD:AB:78:56:34:12 (public)`、`HCI version 5.3`、`ready, GATT service exposed`、手机连接成功;
- init 期间 4 次 + 连接前 1 次 `<wrn> Timeout discarded. No blocking in syswq`(port/lib/net_buf/buf.c:309);
- 用户规律:**先触摸几次再连接 → 一切正常;上电后直接连接 → 首次点按时硬故障**;
- 崩溃特征:IRQ 上下文中跳转到垃圾地址 0x789abcdc(字节模式疑似被 ATT/GATT 数据覆盖),`Push page 1` 之后立刻发生。

**排除项**:rx 事件在 sysworkq(32KB 栈)上处理,无栈溢出;"BT RX WQ"未启动是因 `BT_RECV_WORKQ_BT` 未开(正常);应用主循环未被饿死(Push page 1 已执行)。

**根因(配置级)**:zblue 缓冲池严重不足——
| 配置 | 本板 | allwinner 参考板 |
|---|---|---|
| BT_BUF_CMD_TX_COUNT | 2 | 6 |
| BT_BUF_ACL_TX_SIZE | 27 字节 | 676 |
| BT_ATT_TX_COUNT | 默认(小) | 30 |

手机连接后立即协商 MTU 并做服务发现,ATT 响应远超 27 字节缓冲;sysworkq 上 net_buf 分配不允许等待(直接降级 NO_WAIT 返回 NULL)→ 调用方拿到失败结果 → 内存破坏 → 硬故障。"Timeout discarded" 即分配失败的直接证据。

**修复**(defconfig):`BT_BUF_ACL_TX_SIZE=676`、`BT_BUF_CMD_TX_COUNT=10`、`BT_ATT_TX_COUNT=30`、`BT_BUF_EVT_DISCARDABLE_COUNT=10`。SRAM 77%→79.43%(+12KB),余量约 108KB。

**下一轮测试矩阵**(nuttx.bin 11:17):

B. 连接后静置 30s 再点按
C. nRF Connect 设置里关闭自动服务发现(Service Discovery=manual)再连
D. 先触摸再连接(已知正常,回归用)

### 8.7 第八轮:缓冲池修复实测通过 ✅;新增断连自动重连 + 设置页蓝牙开关

**实机结果**:测试矩阵通过(含原崩溃场景 A)——缓冲池扩容修复确认有效。遗留问题:断开后停在 `BLE: LOST`,手机无法重连。

**原因**:本 zblue 的 `BT_LE_ADV_CONN_FAST_1` 含 ONE_TIME 位,主机不会在断连后自动恢复广播;此前在断连回调(RX 上下文)里重启广播不可靠,失败后状态卡死。

**改动**:
1. 桥接层(`sf32lb52_ble_bridge.c`):
   - `bridge_disconnected` 不再直接重启广播;状态置为 DISCONNECTED(开关关闭时置 OFF);
   - 新增 `ai_watch_ble_bsp_resume_advertising()`:由应用主循环调用,从应用线程执行 HCI 序列(阻塞安全),成功后状态回 ADVERTISING;
   - 新增 `ai_watch_ble_bsp_set_enabled(bool)`:关=停止广播+断开连接(状态 OFF);开=恢复广播(必要时完整 bring-up)。
2. 应用层(`ai_watch_ble.c`):`ai_watch_ble_process()` 在 DISCONNECTED 状态下每秒重试一次恢复广播(默认开启,无开关,即自动重连);新增 `ai_watch_ble_set_enabled()`。
3. UI(`ai_watch_main.c`):设置页新增真实蓝牙开关(lv_switch,默认开,接 `ai_watch_ble_set_enabled`);BLE 状态标签移至开关下方;主题联动配色。

**状态语义**:OFF=开关关闭;ADV=可被发现;ON=已连接;LOST=断连瞬间(≤1s 内自动回到 ADV);ERR=初始化失败。

**待验收**:断连→~1s 内手机可重新扫描到 `AI-Watch-403` 并重连;设置页关蓝牙→首页 `BLE: OFF`、手机不可见;开蓝牙→恢复 `BLE: ADV`。

### 8.8 第九轮:自动重连失效根因 —— 遗留广播集未删除,-EALREADY

**实机结果**:断开后仍停在 `BLE: LOST`,重试广播每秒失败。

**根因**(adv.c 确认,确定性 bug):`bt_le_adv_start_mc()` 先调 `adv_create_legacy()`,若遗留广播集(`hdev->adv`)存在直接返回 `-EALREADY`。ONE_TIME 广播被连接接受后是**停止但保留**集合;断连后的重试因此永远 -EALREADY。而 `bt_le_adv_stop()` 对"已停止未删除"的集合走删除分支。

**修复**:`ai_watch_ble_bsp_resume_advertising()` 在 `bridge_adv_start()` 前先调 `bt_le_adv_stop()` 清掉遗留集合。nuttx.bin 7,900,640 B / 11:50。
