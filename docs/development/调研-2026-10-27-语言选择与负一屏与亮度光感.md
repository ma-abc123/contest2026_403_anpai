## 1. 亮度调节 —— 能做，路径清晰

### 1.1 硬件事实

- 屏是 **1.85" 390×450 AMOLED（CO5300，QSPI）**（`vendor/sifli/boards/sf32lb52/lckfb_huangshan_pi/README_zh-cn.md:50`）[A]。AMOLED 自发光、无背光板，所以"亮度"在驱动里就是**像素发光强度**。
- `co5300.c:112-114` 定义了三个关键寄存器 [A]：
  ```
  REG_WBRIGHT            0x51   /* Write brightness */
  REG_RBRIGHT            0x52   /* Read brightness  */
  REG_WRITE_CTRL_DISPLAY 0x53   /* 显示控制（含亮度生效开关） */
  ```
- 初始化时已经写入：`0x53 = 0x20`（`co5300.c:280`）、`0x51 = 0x7F`（`co5300.c:282`，即 **127/255 ≈ 50% 亮度**）。
- `co5300.c:544` 已有现成函数：
  ```c
  static void LCD_SetBrightness(LCDC_HandleTypeDef *hlcdc, uint8_t br)
  {
      uint8_t bright = (uint8_t)((int)REG_BRIGHTNESS_MAX * br / 100);
      LCD_WriteReg(hlcdc, REG_WBRIGHT, &bright, 1);
  }
  ```
  并在 `co5300.c:598` 挂进了 ops 表 `SetBrightness` [A]。

### 1.2 断点在哪

`SetBrightness` 只存在于 vendor 层的 ops 结构体（`sf32lb_lcd.h:36`）里，**NuttX 的 `lcd_dev_s` 接口没有把它暴露出来**：

- `sf32lb_lcd.c:663` 的 `sf32lb_lcd_setpower()` 只区分 `power > 0`（DisplayOn）/ `power == 0`（DisplayOff），**中间档位全部丢弃** [A]：
  ```c
  DEBUGASSERT((unsigned)power <= CONFIG_LCD_MAXPOWER);   // 上限 100
  if (power > 0) { ...DisplayOn...; priv->power = power; }
  else           { ...DisplayOff...; priv->power = 0; }
  ```
  也就是说 **`/dev/lcd0` 的 `LCD_SETPOWER` ioctl 接受 0~100，但 1 和 100 效果完全相同**。

### 1.3 三条可选实现路径（按风险从低到高）

| 路径 | 做法 | 改动面 | 风险 | 评价 |
|---|---|---|---|---|
| **A. 打通 setpower（推荐）** | `sf32lb_lcd_setpower()` 在 `power > 0` 时额外调 `p_ops->SetBrightness(&priv->hlcdc, power)` | vendor/sifli 一个函数 3 行 | 低 | 不新增设备节点、不破坏现有 `/dev/lcd0` 语义；上层直接 `ioctl(fd, LCD_SETPOWER, 60)` |
| B. 新增字符设备 `/dev/backlight` | 板级注册一个极简驱动 | 新文件 + Kconfig + defconfig | 中 | 语义更干净，但要动 Kconfig 与新节点，收益不抵成本 |
| C. 走 NuttX 亮度框架 | 启用 `CONFIG_FEATURE_SYSTEM_BRIGHTNESS` | 大 | 高 | **明确不做**：该 feature framework 已在 G3 瘦身里关掉（`defconfig` 无此项），为亮度重新拉回来是反优化 |

**建议选 A。** 它还能顺带解决一个体验问题：`LCD_SETPOWER` 传 0 走 DisplayOff、传 1~100 走亮度，语义自洽，不需要新 API。

### 1.4 UI 侧放哪

设置页现在已经是一个 `lv_roller`（主题选择，`ai_watch_main.c:2448`）+ 一个 `lv_switch`（蓝牙，`:2426`）。亮度用同样的 `lv_roller` 最省事，档位建议 **5 档（20/40/60/80/100）**，而非连续滑块——手表上拖滑块容易误触，且 5 档已经足够演示"自动/手动亮度"的故事。

⚠️ **一个必须注意的坑**：`co5300.c:298` 附近有 `parameter[0] = 0xff; LCD_WriteReg(hlcdc, REG_WRHBMDISBV, ...)`。改动 0x51 后是否需要同步改 0x53（`WRDISBV` 位的"亮度生效"开关）**必须先在板上试**：先只改 0x51 看是否生效，不生效再补 0x53 的对应位。这一步无法靠读代码确定 [B]。

### 1.5 验收判据

1. 设置页拖动亮度档 → 屏幕**肉眼可见**变暗/变亮，且不是色调变化；
2. 切到最低档后深色表盘仍可读（2bpp 字 + AMOLED 低亮度下对比度会掉）；
3. 重启后回到初始化值 `0x7F`（不持久化，属正常；持久化依赖 P1-3 flash，暂不做）；
4. 亮度调整后 BLE 连接不受影响（改的是 LCDC 寄存器，与 BLE 无关，但既然有 §1.3 的 vendor 改动，仍要过一遍连接回归）。

## 2. 光强传感器 —— 板上确实有（LTR-303ALS-01），但软件侧零适配

### 2.1 硬件事实（更正）

| 项 | 值 | 依据 |
|---|---|---|
| 型号 | **LTR-303ALS-01**（Lite-On 数字环境光传感器） | 立创硬件文档「传感器」节 [A] |
| 总线 | **I2C1，PA40(SCL) / PA39(SDA)** | 模组 8/9 脚「传感器 I2C1_SCL/SDA」[A]；`sifli_ap.c:610-613` [A] |
| 地址 | **0x29**（7 位） | playbook `references/sensors-i2c.md:32` [A] |
| 供电 | 受 **PA30（Sensor power control，VSYS_1→HR3V3）** 控制，高有效 | 模组 24 脚 + 30p 第 18 脚「当 GPIO 使用时会影响 PA39/PA40」[A] |
| 同总线邻居 | LSM6DS3TR-C **0x6A**（本项目用 `LSM6DSLACCEL_ADDR0`）；MMC5603NJ **0x30** | `sensors-i2c.md:32` [A] |

**这条总线就是 IMU 那条**（`sifli_ap.c:94` `SF32LB52_LSM6DS3_I2C_BUS = 1`，总线以 `sifli_i2cbus_initialize(1)` 初始化、注册为 `/dev/i2c1`）。所以光感**不需要新引脚、不需要飞线、不需要焊任何东西**——它已经在板上、已经通电（只要 PA30 为高，而 IMU 初始化时已经把 PA30 拉高了，`sifli_ap.c:250-251`）。

### 2.2 软件现状：一个器件都没有被识别，但总线是活的

| 检查项 | 结果 |
|---|---|
| `/dev/i2c1` | **已注册**（`sifli_ap.c:635`），IMU 就是挂在这条总线上跑起来的 → 总线本身可用 [A] |
| LTR-303 注册点 | **无**。全树 grep `LTR303` 只命中文档，无任何 `*_register()` 调用 [A] |
| 构建配置 | `CONFIG_SENSORS_LTR308` 等光感驱动**全部未编入**（`cmake_out/prod/include/nuttx/config.h` 无匹配）[A] |
| 树内可用驱动 | 有 `ltr308_uorb.c`、`apds9960.c`、`apds9922.c`、`bh1750fvi.c`、`isl29023.c`、`veml6070.c`——**没有一个能直接用**，原因见下 [A] |

### 2.3 ⚠️ 关键陷阱：LTR308 驱动**不能**直接拿来改 LTR-303

决赛打磨计划 P5-7 写的是"LTR-303ALS（可从 `ltr308_uorb.c` 改）"。方向上没错，但**不能只改地址就用**，两者寄存器布局根本不同：

| | LTR-308 | LTR-303 |
|---|---|---|
| 默认地址 | `0x53`（`ltr308_uorb.c:52`） | **`0x29`** |
| Part ID 寄存器 | `0x06`，期望值 `0xB1`（`:56`, `:54`） | **`0x86`**（不同寄存器） |
| 数据寄存器 | `DATA_0 = 0x0D`（5 字节，含通道+状态） | **`ALS_DATA_0 = 0x88`** / `ALS_DATA_1 = 0x89`（2 字节 16 位） |
| 控制寄存器 | `CTRL = 0x00`、`MEAS_RATE = 0x04`、`GAIN = 0x05` | **`ALS_CONTR = 0x80`**、`ALS_MEAS_RATE = 0x85`，增益在 CONTR 的 bit2:1、积分时间在 MEAS_RATE 的 bit5:3 |
| 状态 | `STATUS = 0x07` | **`ALS_STATUS = 0x8C`**（bit2 = 数据有效） |

`ltr308_uorb.c:233-243` 会读 `0x06` 并与 `0xB1` 硬比对，不匹配直接 `-ENODEV`。**所以把地址改成 0x29 也只会得到 -ENODEV。**

**结论：需要新写一个 `ltr303_uorb.c`，或把 LTR308 驱动做成寄存器表可配的通用 ALS 驱动。** 前者约 250~300 行（照抄 `ltr308_uorb.c` 的 lower-half 结构 + 换寄存器定义），后者更优雅但改动面大、通不过上游评审。**建议新写 driver。**

### 2.4 还缺一环：`/dev/uorb` 是空的

`README_zh-cn.md:247` 原文："**`/dev/uorb` 暂为空——sensor uORB 集成排在后续 PR**" [A]。

这意味着**连 IMU 都没有走 uORB**——本项目用的是老的 `lsm6dsl_sensor_register()` 字符设备路径（`/dev/lsm6dsl0`），而不是 uORB。所以新写的 LTR303 驱动如果照 `ltr308_uorb.c` 走 uORB 路线，还要确认 `sensor_register()`/uORB 框架在本工程被编入。这是**动手前必须先验的一步**（编译一下就知道，成本很低）。

如果 uORB 走不通，还有一个更省事的退路：**照本项目 IMU 的既有做法**，注册成 `/dev/ltr303` 字符设备，走 `read()`/`ioctl()`。对"1Hz 读个 lux 值"这种需求，uORB 的全部机制纯属浪费。

### 2.5 与 BLE 的关系（这是最需要警惕的地方）

`ble.md`「后续规划的影响速查」已经点名：**"P5-7 新 I2C 传感器（i2c1 与 IMU 共享总线，后台线程 + 短事务）"** [A]。

具体风险，按优先级：

1. **总线争用会打到 IMU**：IMU 采样线程 25ms 一轮，每轮 ~42ms 的 I2C 事务（22 次单字节读）几乎把总线占满。再插一个 1Hz 的光感读，理论上只占 0.1% 带宽，但**如果光感读发生在 IMU 事务中间**，SiFli HAL 的 `I2C_TIMEOUT_BUSY` 是 **1000ms**——一旦撞上就是 IMU 采样卡 1 秒，直接造成跌倒算法的采样空洞（P1-1 §2.5 记录过"1.1 秒采样空洞"的危害）。**必须用互斥锁串行化，而不是"反正才 1Hz"**。
2. **探测的代价**：`红线 #2`——对不在线的 I2C 设备做一次探测 = 阻塞 1~2s。所以**绝不能在主循环里探测光感**，必须放进后台线程（或者干脆只在 bring-up 时探测一次，失败就永久放弃）。
3. **1Hz 就够，不要贪快**：人眼对亮度变化的适应时间以秒计，1Hz 采样完全够，2Hz 已是上限。
4. **PA30 别乱动**：光感和 IMU 共用这个 HR3V3 开关。想"为了省电把光感单独关掉"是不可能的，一关两个都死。

### 2.6 现在能不能做：能，但要按"三步走"，且第一步最小

| 步 | 内容 | 风险 | 前置 |
|---|---|---|---|
| **① 点灯验证**（优先，半天） | 写个最小 `i2ctool` 脚本或临时代码，在 `/dev/i2c1` 上读 `0x29` 的 Part ID，确认能读到 `0x86`[B] | **零**（只读，不影响任何现有功能） | 板子接上 |
| ② 最小驱动 | 注册 `/dev/ltr303`，1Hz 后台读 lux，先只在串口打印，**不接任何 UI** | 低 | ①成功 |
| ③ 接到亮度 | 启用手动/自动双模式：自动 = lux 分档映射到 5 档亮度，带滞回（防止临界值抖动）+ 手动覆盖优先 | 中 | ②稳定跑满一天 |

**第 ① 步是整个判断的关键分水岭**：如果 Part ID 读不到，说明要么地址不对、要么器件没上电、要么这颗根本没贴（立创文档写了不等于每块板都贴）。**在①出结果之前，不要写任何驱动代码。**

### 2.7 一个诚实的提醒

答辩故事上，「**LTR-303 读环境光 → 分档自动调亮度**」比"5 档手动"好听得多，而且**硬件是真的**，这不是包装。但要注意两点：

1. **AMOLED 的调亮度是"发光强度"不是"背光"**，所以低亮度下色彩会偏、对比度会变。演示时别把亮度拉到最低讲，会显得屏幕很差。
2. **别承诺"护眼"**：LTR-303 只有 ALS（环境光），没有环境光闪烁检测。说"自动亮度"是准的，说"护眼/防频闪"是错的。

## 3. 语言选择 —— 能做，工作量小

### 3.1 好消息：回退机制已经存在

`ai_watch_main.c:1486` 的 `ai_watch_text_is_ascii()` 已经在用："逐字节扫描，遇到高位就判定为 CJK"。它在提醒列表里已经这样用（`:1593`）：

```c
lv_obj_set_style_text_font(lbl,
    ai_watch_text_is_ascii(text) ? &lv_font_montserrat_16 : &ai_watch_font_cjk_16, 0);
```

也就是说：**"根据内容自动挑字体"这件事，代码里已经做过一遍了。** 要做中英切换，只是把"挑字体"的判据从"这条文本是什么语言"换成"用户选了哪个语言"。

### 3.2 工作量盘点（这才是关键）

我数了一遍所有会出现文案的位置：`lv_label_set_text` 共 **约 60 处**，分布在：
- 应用名注册表 `g_app_registry`（5 个：AI / Timer / Reminder / Settings / Exercise）
- 固定页：表盘、应用列表、设置页
- 5 个应用页 + 跌倒全屏告警 + 提醒条幅
- 动态字符串：`"Steps today"`、`"Walking/Running/Rest"`、`"IMU: starting..."`、`"BLE not connected"`、`"Listening on phone..."` 等

**策略建议：用字符串表 + 指针，绝不用 `#ifdef` 双语各编一份。**
- `#ifdef` 方案会让固件同时只含一种语言，但**要重编重烧才能切**，等于演示时不能切语言——失去意义。
- 字符串表方案：两张 `const char *` 数组（约 60 条 × 2 语言），加一个 `g_lang` 索引，切换时重刷当前页文案。**RAM 开销接近 0**（字符串在 flash），只需一个 `int`。

考虑到 LVGL 9.1，切换时用 `lv_label_set_text_static()`（字符串是 `const` 常量，不复制）而不是 `lv_label_set_text()`，可省掉每次刷新时的堆分配。

### 3.3 字体够不够

`cjk_charset.txt` 是 **3779 个字符 = GB2312 一级字库（3755 汉字）+ 全角标点** [A]。这意味着：
- ✅ 常见中文 UI 文案 100% 覆盖（步数、今日、提醒、跌倒、取消、设置这些全在一级字库）
- ✅ 英文也覆盖（ASCII 从 DejaVu 补进同一字体，`gen_cjk_font.sh` 里 `-r 0x20-0x7E`）
- ⚠️ 二级字库（生僻字）不在，但 UI 文案根本用不到
- ✅ 字体是 `const lv_font_t`（`.h` 里 `extern const`，`.c` 里 `LVGL_VERSION_MAJOR >= 8` 走 const 分支）→ **占 flash 不占 SRAM**，这一点很重要，不用为 SRAM 担心

### 3.4 推荐做法：三选一

| 方案 | 说明 | 工作量 | 评价 |
|---|---|---|---|
| **A. 中文优先，英文兜底** | 全部文案中文化，保留英文作为 fallback（比如设置页加一个语言开关） | 中 | **推荐**。答辩现场用中文最自然，但评审可能更习惯英文 UI，切一下即可 |
| B. 纯中文化 | 只做中文，不做切换 | 小 | 最省事，但失去"双语"这个演示点，也失去兼容性 |
| C. 纯英文不动 | 不改 | 0 | 与"P5-1 UI 中文化"计划冲突，且答辩现场讲中文、屏幕全是英文，割裂 |

**建议 A**，并且**把语言开关放在设置页第一项**（现在是 Bluetooth / Theme / About，语言插最前面）——演示时一进设置就能切，观众看得见。

## 4. AI 负一屏 —— 能做，但有一个隐蔽的坑

### 4.1 页面机制现状（好消息）

`ai_watch_main.c` 的页面管理器已经很规整：

```c
#define AI_WATCH_PAGE_HOME          0
#define AI_WATCH_PAGE_APP_LIST      1
#define AI_WATCH_PAGE_SETTINGS      2
#define AI_WATCH_PAGE_FIXED_COUNT   3
#define AI_WATCH_PAGE_APP_BASE      100
#define AI_WATCH_PAGE_STACK_MAX     8
```
`fixed_pages[]` 数组按 `AI_WATCH_PAGE_FIXED_COUNT` 大小分配，`ai_watch_push_page()` 对 `page < AI_WATCH_PAGE_FIXED_COUNT` 直接从数组取 [A]。**加一个固定页只需改枚举 + 加一个 create 函数**，机制已就绪。

手势侧：HOME 页现在只有"上滑/点击 → 应用列表"（`:3411-3420`），**左右滑是空闲的** [A] —— 负一屏用左滑进入完全无冲突。

### 4.2 ⚠️ 隐蔽的坑：负一屏会挤掉 PIN 码输入的位数

这是我在翻代码时发现的一个**跟负一屏无关、但会被它触发**的问题：

```c
#define AI_WATCH_PAGE_APP_BASE      100
```

`ai_watch_push_page()` 里有两处判断：
```c
if (page < AI_WATCH_PAGE_FIXED_COUNT)          // 固定页
    target = watch->fixed_pages[page];
else if (page == AI_WATCH_PAGE_APP_BASE && ...) // 应用页
```

应用页用的是 `AI_WATCH_PAGE_APP_BASE + app_index` 编码 —— 也就是说：
- 现在 `FIXED_COUNT = 3`，`APP_BASE = 100` → 固定页可用编码 0/1/2，应用页从 100 起，**中间 3~99 是空闲的**
- 如果加负一屏，`FIXED_COUNT` 变 4 → 固定页 0/1/2/**3**，仍远小于 100 → **不会冲突** [B]

结论：**这个坑不存在，页面编码有余量**。我特意去核了一遍是因为这类"枚举扩容撞上某个硬编码的 base"的 bug 在嵌入式里极难查（表现为随机跳页）。记在这里是为了明天动手时心里有数。

### 4.3 负一屏的内容从哪来

**关键约束：手表现在完全不知道"今天走了多少步"以外的任何信息。** 逐项核对数据源：

| 想显示的内容 | 数据源 | 现状 |
|---|---|---|
| 步数 | `snap.steps_today`（`ai_watch_motion_get_snapshot()`） | ✅ 现成 |
| 距离 | `snap.distance_m` | ✅ 现成 |
| 活动状态 | `snap.activity`（REST/WALK/RUN） | ✅ 现成 |
| 活动时长 | ❌ 快照里没有"本日累计活动分钟" | 需在 motion 线程里新增累计（约 20 行） |
| 跌倒事件数 | ❌ 只有 `poll_fall()` 弹出单个事件，无计数 | 需在 BLE 层的 fall 上报处加计数 |
| AI 评语文本 | ❌ 需要手机侧下发（新增 Command 0x06） | 需跨两仓 |

**所以负一屏要分两步：**

**第 1 步（手表侧独立可完成，建议明天做）——"本地数据页"**
- 左滑进入，显示：日期 + 步数 + 距离 + 活动状态 + 一个"连接手机生成 AI 简报"的提示
- 这已经是 P3-1 里定义的**空态兜底**（计划原文："无简报/未连手机时显示本地统计 + 连接手机生成提示"）
- 不依赖手机端任何改动，改动面 = `ai_watch_main.c` 一个页面函数 + motion 快照加一个累计字段
- ⚠️ 但注意：**加 `FIXED_COUNT` 会影响 `ai_watch_update_theme()` 里的页面遍历**，主题切换时要确认新页也调色（这是最容易漏的，切主题时新页变白底黑字就会很难看）

**第 2 步（跨两仓，建议排在第 1 步之后）——接入手机 AI 简报**
- 手表侧：在 `ai_watch_ble.c` 里新增 `0x06` Command 解析 + 一个 `ai_watch_daily_brief_s` 结构体（日期/步数/活动分钟/事件数/评语文本）
- 手机侧：`phone/AIWatchCompanion` 聚合当日数据 → LLM → 下发
- `ble.md` 已明确这条是"只碰协议层、复用 f4 Command、不新增 GATT attribute"，**协议层风险低** [A]
- 评语文本受 `AI_WATCH_REMINDER_TITLE_MAX = 24` 与 `AI_WATCH_AI_TEXT_MAX = 224` 约束，负一屏展示建议单行截断 + 省略号，不要尝试滚动

### 4.4 排序理由

负一屏和语言选择**必须同批做**，原因很简单：负一屏上要写"今日步数""AI 简报"这类文案，如果先做负一屏用英文、后做语言选择再改一遍，等于同一批字符串改两次。**先定语言表，再往表里填负一屏的文案**，一次到位。

### 5.1 开工前的三个前置确认

1. **板子接上**（现在无 `/dev/ttyUSB*`）。亮度改动必须实机看效果，没法靠代码确认。
2. **`co5300.c` 的 0x51 / 0x53 关系先单点验证**：烧一个只在初始化时把 `0x51` 从 `0x7F` 改成 `0x3F` 的版本，看屏幕是否明显变暗。若不变，说明还需要动 0x53 的 `WRDISBV` 位——这一步的结果会决定 §1.3 路径 A 是否需要多改一行。
3. **uORB 是否可用**：如果决定新驱动走 uORB 路线，先编一次确认 `sensor_register()`/uORB 框架在本工程能过；否则直接走 `/dev/ltr303` 字符设备（照 IMU 的既有做法）。

## 6. 顺带记录：三个本次调研中确认的既有事实

1. **`LCD_MAXPOWER = 100`**（`defconfig` 有 `CONFIG_LCD_MAXPOWER=100`）——亮度取值范围天然就是 0~100，不需要改 Kconfig。
2. **`setpower` 里的 `DEBUGASSERT`** 在 `CONFIG_DEBUG_ASSERTIONS=y`（defconfig 已开）下是**生效的**。所以如果上层传 >100 会直接断言炸掉，加亮度 roller 时务必钳位。
3. **光感与 IMU 共用 PA30 的 HR3V3 供电**——`sifli_ap.c:250-251` 在 IMU 初始化时已拉高，所以光感**现在就是通电的**，第 0 步不需要额外做上电动作。
