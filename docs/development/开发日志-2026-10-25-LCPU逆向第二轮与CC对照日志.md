# 开发日志 2026-10-25：LCPU 逆向第二轮结论与 host 侧 CC 对照日志

## 背景

逆向方第二轮报告（`/home/ma/lcpu-re/analysis/REPORT_ROUND2.md`，分析
`handoff_2026-10-25/` 的 18 份故障快照）推翻了"控制器跑飞/断言"假说：

1. 18/18 份快照 `0x20407FE0` 断言记录全 0、cfg 魔数与 hook 完好——控制器是
   **静默停住**，没有崩溃。
2. 控制器已经把对应命令的 Command Complete 事件 staged 到 L2H 发送口
   （`0x2040F844`），KE_EVT2 线程栈与健康快照一致，L2H 环为空——**事件已交出，
   host 侧却报命令超时**。
3. 早期 6 次故障的 Reset（0x0C03）CC 状态字节是 **0x83**（标准 HCI 错误码只到
   0x42，非标准），后期 12 次 CC 正常但故障点在初始化序列中游移。
4. 恢复代码的 opcode 标注只有 4/18 与实际相符，不能用于归因（已由 097f724
   的 first-fault-wins 缓解标注互相覆盖，但标注≠根因）。

结论：嫌疑转向 **HCPU 侧的 CC 交付/命令完成逻辑**（CC 没到 HCI 层，或到了但
没完成等待）。

## 本轮代码改动（按报告 §7.1 "只做三件事"）

版本 `4.8.13-cclog`（diag 构建，`CONFIG_AI_WATCH_ROMDUMP=y` 保留）。

### 1. CMD/CC/CS 对照日志（只加观测，不改行为）

- `external/zblue` `hci_core.c`：
  - `bt_hci_cmd_send_sync()` 入口：`CMD opcode=0x%04x wait_ms=10000`（INF）；
  - `hci_cmd_complete()`：`CC opcode=… status=… credits=…`（status!=0 用 WRN）；
  - `hci_cmd_status()`：`CS opcode=… status=… credits=…`。
  - 级别选择依据：实测本构建 `<inf>`/`<wrn>` 均上串口（Identity 即 hci_core
    的 LOG_INF）。CMD 与 CC 按 opcode 一一配对，用于裁定报告 §7.2 四种情形：
    CC 到了没完成（host 状态机）vs CC 根本没到（L2H 交付）。
- zblue `hci_cmd_done()` 原有的两个"收到 CC 但不唤醒等待者"分支（无 sent_cmd、
  opcode 不匹配）本就带无条件 LOG_ERR，本轮不动，靠与 CC 行配对判读。

### 2. 命令完成逻辑修复（0x83 策略）

复核结论：本 port 的 `hci_cmd_done()` 对**任意 status** 都会释放同步信号量
（`cmd(buf)->status = status; k_sem_give(...)`），"status!=0 不完成等待"在这份
代码里不成立；真正会吞 CC 的只有上述两个非唤醒分支。因此本轮不改动完成语义，
只新增 0x83 处置链：

- zblue：`bt_hci_cc_status_cb_register()`（模式同 cmd_timeout 回调）。CC/CS
  出现非标准状态 0x83 时上报（opcode、status、连续次数 streak）；任何
  status==0 的 CC/CS 清零 streak。
- `vendor/sifli` bridge：`bridge_cc_status_notify()` 以 first-fault-wins 锁存
  新故障类型 `CC_STATUS`（recover 日志标注 `cc-status`）。应用主循环照常走
  `ai_watch_ble_bsp_recover()` = 强制 teardown + LCPU 停机重启，替代应用层
  initfail 软重试的"原地重发 Reset"。恢复路径本身就断链/停广播/重启 LCPU，
  连续 3 次 0x83 的"断电升级"由恢复后再次锁存自然达成。

### 3. 明确不做（报告 §7.3/§7.5）

- 不给 LCPU ROM `FUN_503E8` 的无界重试打硬件补丁（快照未证明被触发，留待
  host 侧对照实验定方向后再决定是否用 30/31 两个空闲 patch 通道）；
- 不再追 `ai=`/`0x2040FDA0`；不等 Hardware Error 自然复现；
- 不用 recovery opcode 标注做归因。

## 实战结果（15:17–15:31 采集窗口）

烧录后板子复位循环问题排查为 sftool 读回参数误用（非固件问题）；正确语法
`read_flash <file>@<addr>:<size>` 触发软复位后完整启动。

首个采集窗口即抓到 **2 次连接期 Hardware Error**（此前 faultcap 版本一直没
在连接期复现过）：

- 事件 01：`1792913006.881`，广播后手机连接，`CMD 0x2030`→`CC 0x2030
  status=0x00` 完成后 324ms 控制器上报 Hardware Error code 0；
- 事件 02：`1792913195.813`，恢复→重新广播→重连后约 1s 同样死亡。

两事件期间另有 2 次 8 秒正常会话干净断开。CMD/CC 全程按 opcode 配对
（79 CMD / 77 CC + 0 CS），仅有的 2 条未配对 Reset 来自 sftool 误用打断的
启动，非固件；无超时、无非零 status CC、无 `No command sent`/`instead of
expected`。**硬件错误型故障下 host 侧完全清白，控制器在连接建立后自行死亡。**

两份故障快照（64KB LPS，双遍 union 合并 0 缺失）与第二轮 18 份同签名：
flag=0、hooks/cfg 完好、无断言；这次 KE_EVT2 栈上连发送路径热点返回地址
都没有（0/0/0）。send-port staged 碎片（`00 02 00 18` / `00 00 00 00`）
与 L2H 环残留（初始化 CC 序列）已记入 README_R3 供分析方核验。

第二轮的"初始化超时"型（18 连发）本窗口未复现，采集进程持续运行，
`split_r3_events.py` 可增量切分新事件。
