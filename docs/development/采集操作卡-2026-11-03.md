## 1. 采集流程（一条命令 + 一个窗口）

采集固件的行为：**上电就连续记录，不需要按任何键，蓝牙不启动**。串口每秒滚出
约 25 行 `REC,<t_ms>,<x_mg>,<y_mg>,<z_mg>,<gx>,<gy>,<gz>`。

屏幕坏了，所以提示不要看终端，改成电脑上一个大窗口：

```bash
cd /home/ma/openvela-contest403/contest2026_403_anpai
tools/run_capture.sh                      # 默认日志 ~/huangshan-logs/cap_run1.log
```

脚本会自动停掉投屏（它独占串口），退出时自动恢复。窗口里：

- 按 **空格** 开始计时（先 25 秒静置），**F** 全屏，**Esc** 退出
- 顶部：采样率 / 样本数 / 断流数（采样率掉到 20 以下会变红）
- 中部：**第几个动作 + 剩余秒数（超大字号）**，最后 2 秒提示下一个动作
- 横幅：`检出！`（红）/ `冲击但被驳回`（黄）
- 底部：18 个动作清单，做完的自动打 `检出 OK` / `未检出 ✗`，并显示该段计步数（`步 0 OK` / `步 3 ✗`）

命令行版仍在（不需要图形界面时用）：`tools/capture_monitor.py --log <文件>`。

| 57–65 s | 站立 -> 前倒在床垫 | **应检出** · 0 步 |
| 65–73 s | 快速坐下（椅子） | 不应检出 · 0 步 |
| 73–81 s | 重重坐下（屁股砸椅子） | 不应检出 · 0 步 |

**计步校准**：`0 步` 的动作段是误报样本（端杯子、挥手、打字、穿脱外套
最容易有幻影步），`应有步` 的走路段是漏计样本。采完 `capture_analyze.py`
会逐段给出「步 N OK/✗」，据此决定 `STEP_PEAK_MG`（当前 1150 mg）往哪调。

## 2. 三个注意点

1. **手表必须戴在手上做动作**，不要拿在手里甩——目标场景是佩戴状态，拿在手里的
   加速度特征完全不同，采了也不能用来调参。
2. **跌倒只往床垫/软垫上倒**，不要硬地真摔。今天采的是特征分布，不是破坏力。
3. **USB 线放松**：线从身侧自然垂下，不要绷紧。线绷紧会拉住自由落体、缓冲冲击
   峰值，这是本轮采集唯一的系统性误差来源。同一动作做多次就是为了在分析时看
   方差——某次差异特别大，就把那一组剔除。

## 4. 采集构建与正常固件的三处差异

| 项 | 正常固件 | 采集构建 | 为什么 |
|---|---|---|---|
| 蓝牙 | 启动并广播 | **完全不启动** | 采集期间控制器每 10 s 一次 recovery（HCI 超时 + LCPU patch 重载，约 1.15 s），期间采样线程抢不到 CPU，日志里表现为周期性空洞、丢约 10% 样本。采集不需要蓝牙 |
| 告警倒计时 | 15 s | 3 s | 采集时不弹 UI，倒计时只决定"多久能再判定"；8 s 动作间隔够用 |
| 事件冷却 | 60 s | 3 s | 否则连续 3 次跌倒只有第一次能触发，后两次被冷却期静默吞掉 |

**判定阈值一个都没改**：550/2400/2000/50°/80/200/4500 与正常固件完全一致，
所以采集数据的"是否触发"结论可以直接迁移到演示固件。离线回灌时
`capture_analyze.py` 默认已按 3 s/3 s 计算；若要回放正常固件的日志，
加 `--cooldown 60000 --countdown 15000`。

## 5. 已知的干扰项（采到了不用管）

- **有效采样率 25 Hz**（间隔稳定 40 ms）：配置写的是 25 ms，`usleep` 在本板
  tick 精度下实际是 40 ms。正常固件也是这个速率，所以采集数据与真实运行一致；
  离线回灌按真实 `t_ms` 计算，不假设固定周期。
- **告警 UI 在采集版里是关的**：跌倒状态机照常判定、照常打日志
  （`MOTION: fall armed` / `impact but orientation kept`），只是不弹倒计时。
- **采集版没有蓝牙**：串口不会再出现 `controller recovery` / `lcpu patch` 一类行，
  这是正常的，不是 BLE 坏了。
