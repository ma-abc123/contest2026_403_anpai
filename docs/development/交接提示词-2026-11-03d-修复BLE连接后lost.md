## 2. 症状精确定义（这才是要修的东西）

用户明确：**BLE 启动可以自愈，几次重试后基本能正常广播**；启动延迟不是当前痛点。真正的问题是**手机一连，手表端总抛 `lost`**。

- `BLE: LOST` 是 UI 状态字符串，定义在 `app/ai_watch/ai_watch_ble.c:959`，对应枚举 `AI_WATCH_BLE_BSP_DISCONNECTED`（`app/ai_watch/ai_watch_ble_bsp.h:85`，注释 "was connected, link lost"）。
- 状态由 `bridge_disconnected()`（`vendor/sifli/chips/sf32lb52/sf32lb52_ble_bridge.c:528-572`）在断连回调里置为 `DISCONNECTED`，随后主循环 `ai_watch_ble_process()` 驱动重新广播。
- **串口日志里不会出现 "LOST" 字样**，要找 `disconnected, reason ... duration_ms=...`、`Hardware error`、`controller recovery type=...`。
- 断连不是应用层逻辑写错，而是 **LCPU 控制器固件崩溃 → 强制 teardown → 拆链**。

### 3.2 三个 blob 的关系（已二进制验证）

- 官方原版 `vendor/sifli/middleware/bluetooth/patch/sf32lb52/sf32lb52_lcpu_patch.h`，sha `d7f9097b40c2b92e2a7d383e88b9a6ce90b7cc114f2acb14c2e99e8f38bba78c`，`g_lcpu_patch_bin` **2024 words**。

- E1 = 当前 HEAD 的 `sf32lb52_lcpu_patch_exp.h`，sha `6104cb58885a6c7afca6b9d389aa6c5f39927d26c3fc08c626cbe4022fdfdc63`。与 pre_e1 只差 `g_lcpu_patch_bin` 的 **idx 1164–1171 共 8 个 word**；E1 把这 8 条指令全改成 `0xbf00bf00`（双 NOP）——这就是用户说的"通过反编译修复但没完全修好"的 blob。

## 4. 已排除 / 不要再重复的方向

1. **LCPU blob 内容**（官方 / pre_e1 / E1，差 8～1490 words，广播结果一致）。
2. **换回官方 blob**（用户问过，2/8，修不好，已按意愿保留 E1）。
3. **4.8.56 之后应用代码差异**（整机回退 4.8.56 仍 3/8）。
4. **运动线程栈 8 KB vs 16 KB**（4.8.71 实测 16 KB 未消除连接期 Hardware Error）。
5. **headless LVGL 全帧 PSRAM 条带**（4.8.74）。
6. **LVGL sysmon / perf / INFO printf 开关**（4.8.76）。
7. **缩短 INIT_FAILED 恢复阶梯**（历史 A/B：3/8 → 0/8，明确有害；现为 10/15/20/30/60/120 s，上限 300 s）。
8. **「断电 ≥5 min 冷却」**（用户明确否定；8 轮彩票中成功/失败在轮次间随机分布、换镜像后首轮即可成功，非累积剂量效应）。**不要再把断电冷却写成修复手段或前置条件。**
9. **DISCONNECTED >20 s → recover() 升级**（代码里试过并主动移除，`ai_watch_ble.c:1196-1207` 留有 NOTE：full teardown 含 LCPU warm reset，会累积 dose 让下次 bring-up 更差）。
10. **把"能广播"当"能连接"**。
11. **4.8.73 TX 串行化已"修好连接"**这一说法：用户当时反馈「等待开机恢复后连接稳定」，但**现在仍反馈总抛 lost**，该修复未被证实；不要撤销它，也不要把它当已解决。

## 5. 未证实的假设（按优先级，含最小单变量 A/B 设计）

- **H1（最强，优先验证）**：连接建立后 **~2 s** 是崩溃窗口。证据：4.8.39 的 `duration_ms` 集中在 244 / 572 / 1447 / 2014 ms；`Device is not subscribed to characteristic` 出现在 `Hardware error` 之前；`ai_watch_ble.c:226-236` 的 TX worker「fresh-link settle」正好是 `now.tv_sec - g_conn_since < 2` 的 2 s 闸门；4.8.73 的串行化就是为「TimeSync 后 Status 撞上 2 s 静默期」而做。
  **A/B**：把 2 s 改成 4 / 6 / 8 s，或改成「等 CCC 订阅完成标志 `g_status_ccc`/`g_data_ccc` 置位后再放行首发通知」，跑 ≥5 轮 `ble_connect_test.py --hold 45` 对比 `DIED_HOLD` 率。注意保留 4.8.73 串行化，检查改动是否引入新并发点。
- **H2**：`g_lcpu_rf_cal_disable != 0` 导致 `sf32lb52_lcpu_boot.c:176-203` 的 100 ms settle + MAC+0x00 bit31 等待被跳过 → 首个 `0x0c03` 无响应。boot.c 内 `lcpu_disable_rf_cal()`（210-213 行）**没有调用点**，为何该 static 变量非 0 尚未查清，怀疑与 `chips/drivers/cmsis/sf32lb52x/bf0_lcpu_init.c` 的同名函数 / 链接覆盖有关。
  **A/B**：去掉 `if (g_lcpu_rf_cal_disable == 0)` 的 gate 强制走 settle，不改 blob、不动恢复阶梯、不动 TX，8 轮广播彩票。
- **H3（应用层，可修体感但不治本）**：`sf32lb52_ble_bridge.c:1037` 里 `resume_advertising()` 只要失败一次就 `resume_retry_after = now.tv_sec + 30`，而 `ai_watch_ble_process()` 每 1 s 的 poke 被 `1006-1007` 的 gate 全挡住 → 手表**长时间死在 LOST**。改成分级退避（2/5/10/30 s）或成功即清零，可显著改善用户体感；**但不能消除控制器崩溃**。改前务必读 `ai_watch_ble.c:1196-1207` 的 NOTE，别顺手加 recover()。
- **H4**：host 侧 HCI 同步路径。基线 8 轮中出现 2 次 `sem_waitirq.c:137` 内核断言（`bt_hci_cmd_send_sync+0x99`），疑超时 / teardown 并发破坏信号量，属并发缺陷而非纯等待。
- **H5**：`defconfig:65 CONFIG_BT_DEBUG_LOG=y` + `:252 CONFIG_BT_DEBUG_LOG_LEVEL=6` 的高频串口输出干扰 HCPU/LCPU 时序。4.8.76 关的是 LVGL 的 INFO printf，**没关 BT debug log**，这是未试过的单变量。
- **H6**：LCPU 固件闭源 blob 内部 assert（`assert_over=2`、`Hardware error code 0`）。E1 反编译 NOP 掉 8 条指令未解决；根治需要厂商固件更新 / assert 说明 / JTAG。若无外部条件， realistically 只能做规避（H1/H3）。
