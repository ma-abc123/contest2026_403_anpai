## 2. 地雷一：改 defconfig 内容永远不会触发重配

**现象**：FULL=1 `build403.sh` 构建成功、版本串 4.8.6-g1 进了 bin（源码改动生效），
但 map 里 lvgldemo 仍在、构建树 `.config` 仍是 `=y`——defconfig 修改被整体忽略。

**根因（两层跳过叠加）**：

1. `nuttx/CMakeLists.txt:387` 只在 `.config` 不存在、或 `NUTTX_DEFCONFIG` **路径字符串**
   与缓存值不同时才从 defconfig 重建 `.config`——改内容不改路径不触发；
2. `build/envsetup.sh` 的 `m` 只在 `CMAKE_BINARY_DIR` 不存在时才执行 cmake configure
   （`_do_cmake_generator`），build403.sh 的 FULL=1 走 build.sh 对已存在目录直接跳过。

**对策（本组起固化为流程）**：每组用**全新构建目录**直接走 cmake：

```bash
cmake -B cmake_out/contest2026_403_ai_watch -S nuttx -G Ninja \
  -DBOARD_CONFIG=/home/ma/openvela-contest403/vendor/openvela/boards/contest2026_403_ai_watch/configs/ai_watch \
  -DCUSTOM_MODULE_PATH=/home/ma/openvela-contest403/build/cmake \
  -DCMAKE_C_COMPILER_LAUNCHER=ccache -DCMAKE_CXX_COMPILER_LAUNCHER=ccache \
  -DEXTRA_FLAGS="-Wno-cpp -Wno-deprecated-declarations"
cmake --build cmake_out/contest2026_403_ai_watch --parallel 12
```

（EXTRA_FLAGS 与 4.8.5 基线 CMakeCache 一致，避免把额外变量混入组间对比。）

**待办**：build403.sh 增量路径对 defconfig 修改完全失明，值得修（mtime 哨兵或对 `.config`
做 savedefconfig 比对）；本组先用全新目录绕开。

## 3. 地雷二：apps 源码目录里的旧生成头文件遮蔽新配置

**现象**：配置真正生效后的构建链接失败：
`libapps_builtin.a(builtin_list.c.o): undefined reference to 'lvgldemo_main'`，
而构建树里新生成的 `builtin_list.h` 已无 lvgldemo。

**根因**：`apps/builtin/` 源码目录残留 `builtin_list.h`/`builtin_proto.h`

教训：**make 流程与 cmake 流程在同一工作区混用时，make 的源码目录生成物会污染 cmake 构建**；
今后跑过 make 构建后需清理 `apps/builtin/{builtin_list.h,builtin_proto.h,.built,.depend}`。

## 5. 发现（非 G1 引入）：BLE 启动期广播失败是死胡同状态

实机出现一次开机 BLE 不可用，日志序列：

```
dev:0: Sending HCI_RESET
lcpu patch: revid=3 -> legacy patch
<inf> Identity: CD:AB:78:56:34:12 (public)      ← 控制器在位，应答正常
<wrn> Controller unresponsive, command opcode 0x2005 timeout  ← LE Set Random Address（原误标广播使能，见第 10 节修正）
aiwatch-ble: advertising start failed: -110
```

分析（`sf32lb52_ble_bridge.c`）：

- `bridge_bt_ready()` 中 `bridge_adv_start()` 失败 → `state = INIT_FAILED`；
- `ai_watch_ble_bsp_resume_advertising()` 仅在 `DISCONNECTED` 态工作，INIT_FAILED 不重试；
- 设置页蓝牙 off→on 走 `set_enabled(true)`：`g_bridge.started` 仍为 true，bsp_start 直接
  return，随后对已僵死控制器再发 adv 命令只会再次超时；
- 现有自愈（`bt_hci_hw_error_notify` → `take_hw_error`）只覆盖 **Hardware Error 事件**，
  不覆盖命令超时。

即：**启动期广播失败后控制器无法从手表侧恢复，只能断电重启**。08-30 记录确认该 LCPU
时序型僵死为随机问题、胖固件同样出现（本组同版本固件亦有一次 BLE 完全正常的开机），
**与 G1 瘦身无关**，但直接阻碍每组回归清单的 BLE 项。

**改进实施（4.8.7-sh，当日完成）**：应用侧自动恢复，**无需改公共仓**（`recover()` 与状态查询
本就在 `ai_watch_ble_bsp.h` 暴露给应用）。`ai_watch_ble_process()` 新增：进入 `INIT_FAILED`
后 10s 首次尝试 `ai_watch_ble_bsp_recover()`，其后每 30s 一次、**上限 3 次**（防止控制器
彻底坏了时每 30s 冻结 UI 3-5s）；到达 ADVERTISING/CONNECTED/DISCONNECTED（链路活跃态）
或 HW Error 事件或用户切换蓝牙开关时计数清零；OFF 态故意不清零（recover() 的异步
re-bring-up 会经过 OFF）。固件 4.8.7-sh 实机验证正常启动 + BLE 全链路无回归破坏；
**自动恢复触发路径未实测**（INIT_FAILED 是随机低概率事件，无法按需复现）——待自然复现时
观察 "INIT_FAILED, auto-recover attempt N" 日志，诚实标注。原计划的 vendor_sifli 公共仓
改动由此省去，后续若要在桥接层内做（含 DISCONNECTED 态 resume 失败的同类死胡同）再走 PR。

## 7. 串口调试工具注脚

`pkill -f "cat /dev/ttyUSB0"` 会匹配杀掉执行它的 shell 自身（命令行含同串），
用正则括号 `pkill -f "cat /dev/ttyUSB[0]"` 规避；注意 `nohup bash -c '...; exec cat ...'`
启动的进程经 exec 后 cmdline 变为裸 `cat /dev/ttyUSB0`，杀它要用不含 "exec" 前缀的模式，
且**启动读取与 pkill 不能放在同一条 bash 命令里**（同串自匹配，本日两次踩中，
其中一次导致烧录命令整个没执行）。
USB 拔插后旧读取进程持有死 fd 表现为"进程活着但 0 字节"，必须重启读取并校验
`/proc/<pid>/fd` 指向当前设备节点。

**串口读取进程与 sftool 不能并存**：两个进程同时读同一 tty 会互抢字节，sftool 的
ROM 同步握手 ACK 被读取进程偷走 → `Failed to connect to the chip`。烧录/读取 flash 前
必须杀干净所有读取进程（含 exec 后的裸 cat），烧完再挂读取 + `read_flash 16` 触发复位抓 boot。

## 8. 今日最大发现：供电不足 + RTS 线电平（BLE"玄学"的统一解释）

### 8.1 RTS/DTR 线电平直接控制芯片复位（实锤）

现象链：开机黑屏需多次重插 → 完全黑屏且串口 0 字节（连 SFBL ROM 横幅都没有）→
用户关键观察：**同一板子插电脑（两根线两个口）全黑，插手机充电头就正常亮**。

pyserial 线电平实验（2026-10-24）：

- 打开串口（pyserial 默认拉起 DTR/RTS）→ 板子死寂 0 字节
- **释放 RTS → 板子立刻完整启动**（boot 全绿）
- 再拉起 RTS → 又死（0 字节）；再释放 → 又活

结论：**板子复位电路受 CH340 RTS 线电平控制**。主机侧任何把 RTS 拉在保持电平的状态
（pyserial 打开串口的默认动作、sftool 异常退出残留）都会把芯片摁死；充电头不给 CH340
供电、引脚悬空，板子靠自身上下拉正常启动。sftool 的 default_reset 正是主动利用这条线。

**运维修复**：监控脚本（python3，打开串口后立即 `dtr=False; rts=False` 再读，设备
消失自动重连续录、行首时间戳）成为标配；黑屏不用拔插，释放线电平即活。

### 8.2 供电不足导致 LCPU 在射频操作瞬间掉电（高置信，待实测坐实）

A/B 定案裁剪清白：把早上备份的 **4.8.5 基线 bin 烧回**（用户对 G1 裁剪的怀疑合理），
同样的死法原样复现——广播正常起来、手机连接 4 秒后 `Hardware error, hardware code: 0`
（连接瞬间 LCPU 暴毙）、自愈触发。**G1（SRAM 仅 -1,632 B）与 BLE 故障无关。**

用户观察 + 全部当日日志统一解释：**PC USB 口电流（~500mA）+ 线材/接头压降撑不住
射频发射电流尖峰**，3.3V 在尖峰瞬间被拉穿 → LCPU 掉电：

- 来得及报错 → `Hardware error code 0`（连接建立瞬间死，08-30 记录的同款）
- 死得太快 → `Controller unresponsive, opcode 0x2005/0x2036 超时`（广播配置序列中的
  命令未完成——0x2005=LE Set Random Address、0x2036=LE Set Ext Adv Parameters，
  原误标为广播使能，见第 10 节；当日以 silent wedge 形式反复出现）
- 充电头（2A）→ 电压稳定 → 全链路正常（用户实测"插充电头直接就连上了"）

8-30 的"随机 Hardware error"很可能同根因——当年自愈机制实际是在给供电边际打补丁。
**待坐实**：带独立大电流电源的 USB HUB 下串口+BLE 应同时稳定；板上电池接入情况待确认。

## 10. 大佬评审修正与后续诊断（2026-10-24 晚）

外部评审对本日记录做了关键修正，已逐条对照代码验证属实：

1. **opcode 标注修正**（zblue hci_types.h:1197/1255/1671/1713/1722）：
   0x2005=LE Set Random Address（非广播使能；本机 CONFIG_BT_PRIVACY=y，广播建立
   流程会发）；0x2036=LE Set Ext Adv Parameters；0x2038=LE Set Ext Scan Response
   Data；真正的使能命令是 0x200A/0x2039。→ signature A 的准确定性是"**广播配置
   序列中某条命令未完成**"，死点分布在 Random Address/Ext Adv Params/Scan Rsp
   Data 等不同阶段，不能归并为"死在使能那一刻"。
2. **assert_over=2 不是计数**：HAL_LCPU_ASSERT_INFO_get 在标志位≠0xa5a5a5a5 时返回
   HAL_BUSY(=2)（bf0_hal_lcpu_config.c、bf0_hal_def.h:36）——含义是"assert 完成标记
   未被观察到"，不能证明断言次数或断言处理流程完整执行。
3. **"全新 LCPU"非断电**：lcpu_power_off()=HAL_RCC_Reset_and_Halt_LCPU(0)，
   reset/halt 而非电源域断电，retention SRAM/模拟状态可能残留——自愈后的环境
   并非干净冷启动。
4. **NVDS/RF 校准损坏假说降级**：sf32lb52_bt_prepare_stack_nvds() 每次 enable 都向
   SRAM 写默认 NVDS，RF 校准（bt_rf_fulcal）在 LCPU release 前全流程执行；固定
   损坏更可能表现为可重复异常而非随机。/dev/config0 dump 低 ROI，撤回。
5. **G1 影响机制评估**（评审排序）：最可能是 BSS 缩小 → 堆起点移动
   （sifli_start.c:50）暴露潜伏内存问题；邮箱为固定地址 + 0x500 保留，G1 不移动
   邮箱。补丁 blob 随链接移动属可检验项（比对镜像内 blob 哈希，待做）。
   **→ 已验证（当晚）**：从 G1 镜像提取 legacy 三段数据（patch_bin 0x1fe0 /
   lcpu_bin 0x1620 / patch_list 0xf8，G1 @0x1247acf8/0x1247cdd0/0x1247ccd8），
   在 4.8.5 基线镜像中逐字节搜索，**三段全部找到且 sha256 一致**（仅地址平移
   ~22KB）——机制 3（补丁内容随链接改变）排除；剩余主要嫌疑收敛到机制 1
   （堆布局暴露潜伏内存问题）。

**当前判读**：signature B 最可能是既有 LCPU 控制器内部故障；signature A 可能同源，
也可能是 HCPU↔LCPU IPC/HCI 响应路径问题——两者暂不能合并；"G1 提高发生率"
未被证明也未被排除。

**诊断动作（进行中）**：构建 LOG_LEVEL=7 + 函数名/行号 的成对诊断 bin
（diag_base=4.8.5 配置 / diag_g1=G1 配置，源码同为本版，trace 配置完全相同），
hci_core.c:466/560 的 LOG_DBG 将给出逐命令发送/应答序列（含 opcode 可读名）——
目标是找到"最后成功的命令 → 第一条无响应命令"；之后再按评审方案做交替冷启动

### 10.1 DBG=7 抓取结果（diag_g1，diag_base 两次均在内核横幅附近早挂，未取到 trace）

**健康参考序列**（全部 status 0x00，~20ms 完成）：
`0x0c03 HCI_Reset → 0x1003/0x1001/0x1002 读特性/版本/命令 → 0x2003/0x2002/0x203a/0x0c6d
LE 参数 → 0x2001 事件掩码 → 0x0c56/0x0c45/0x0c13/0x0c24/0x0c18 → 0x080f/0x0c01/0x1009
→ 0x2005 Set Random Address（隐私 RPA）→ 0x2036 Ext Adv Params → 0x2037 Adv Data →
0x2038 Scan Rsp → 0x2039 Ext Adv Enable → 0x2030…` 随后手机连接成功。

**失败点地图（本日全部样本）**：0x0c03（HCI_Reset 本身，自愈重启后）、0x1003
（Read Local Features，第 2 条命令）、0x2005、0x2036、0x2038——**在早期命令序列中
均匀随机分布**，并非集中于广播命令。失败形态：命令正常发出（h4_send 日志在），
控制器 10 秒无应答（HCI_CMD_TIMEOUT），此后彻底不应答。

**用户新观察并入**："到了 ON 但授时没成功、随后 LOST"——连接建立后的 GATT 交换
也会缺失/掉链，与启动失败同族：会话中间也可能丢响应/事件。

**新头号假说：H2L 环形缓冲武装竞争（vendor 侧可修）**。`sf32lb52_bt_controller_enable`
