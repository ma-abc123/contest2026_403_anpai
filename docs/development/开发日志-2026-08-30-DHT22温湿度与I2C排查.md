## 1. 背景：心率血氧（MAX30102）接线验证

计划将 MAX30102 接至 30P 排针 29/30 脚（PA11/PA10，丝印 I2C0），与板载 AW32001 充电芯片共享 I2C 总线。地址核查：MAX30102=0x57、AW32001=0x49、LSM6DS3=0x6A，互不冲突，I2C 多设备共享成立。

### 1.1 引脚归属疑点（未定论）

固件中 I2C2 控制器的引脚被配置了两次：

- `bsp_pinmux.c` `BSP_PIN_Common()`：PA10/PA11 → I2C2（注释：充电芯片）
- `sifli_ap.c` bringup（LSM6DSL 启用时）：PA39/PA40 → I2C2（LSM6DS3 实测在此工作）

两对引脚是否同时挂在 I2C2 内部功能网（HAL 闭源，无法从源码判断）决定了 A10/A11 的外部接线是否属于同一总线。

### 1.2 启动 I2C 扫描（4.5.1）

因 ai_watch 占用串口无法进 NSH，在应用启动时对 `/dev/i2c0`、`/dev/i2c1` 全地址扫描（0x08–0x77），结果打印到串口日志。

技术要点（复用时注意）：

- 探测方式照抄 i2ctool 默认：**1 字节读**（`I2C_M_READ`，length=1）。
- **SiFli HAL 拒绝零长消息**：`HAL_I2C_Master_Transmit` 对 `Size == 0U` 直接返回 `HAL_ERROR`，i2ctool 的 `-z`（零字节写）探测在本平台不可用。
- 已知设备的裸读假阴性：FT6146 对"不写寄存器直接读"会 NACK，因此总线 0 扫描显示 no devices 属正常，触摸实际工作正常。

### 1.3 实机观察（日志 ai-watch-20260830-192751 / 194237）

```
i2c-scan: /dev/i2c1 (charger / accel / MAX30102)
i2c-scan:   0x29 ACK
i2c-scan:   0x30 ACK
i2c-scan:   0x6a ACK = LSM6DS3 accel
```

- `0x6a` LSM6DS3 正常，I2C2 控制器本身工作。
- `0x57`（MAX30102）未出现；**接线前后扫描结果一字不差**——接线动作对总线零影响，是"A10/A11 未挂上 I2C2"的强证据（未最终定论）。
- `0x49`（充电芯片）未应答：可能纯 USB 供电（无电池）时 AW32001 不上电，也可能该板充电 IC 实际不走此控制器。不影响现有功能（固件平时不与其通信）。
- `0x29`/`0x30` 幽灵应答：接线前即存在，与用户模块无关，疑似某未上电设备的寄生 ACK。

### 1.4 pinmux 诊断（4.5.2，已撤除）

用 `HAL_PIN_Get(PAD_PA10/11/39/40, ...)` 读 FSEL 实际复用状态的设计已实现并编译通过，可一锤定音。因供电问题整体搁置，随诊断一并撤除（未提交）。回学校验证时重新引入即可，思路：

1. 烧录带 pinmux 打印的固件，看 `PA10/PA11` 是否 = `I2C2_SCL/I2C2_SDA`。
2. 是 → 模块接线/供电问题；否 → 在 bringup 里重新 `HAL_PIN_Set` 挂回 I2C2 再扫。

## 2. DHT22 温湿度（4.6.0）

### 2.1 引脚决策：PA20（排针 24 脚）

候选排除过程：

| 候选 | 结论 |
|---|---|
| PA_32（17 脚） | 固件配为 GPTIM2_CH1 LED，占用 |
| PA_24/25/27/28/29（19–23 脚） | TF 卡：defconfig `BSP_USING_SPI1=y` + `MMCSD=y`，全部占用 |
| PA_19/18（25/27 脚） | 调试串口，占用 |
| PA_34/43（26/28 脚） | KEY1/KEY2，占用 |
| PA_36/35（13/15 脚） | USB，占用 |
| PA_30（18 脚） | LSM6DS3 LDO 使能，占用 |
| "PB_39"（wiki 14 脚） | **证伪**：SF32LB52 pad 枚举无 PB39（L 域仅 PB00–03/PBR0–3），wiki 疑为 PA_39 笔误（传感器 I2C SDA，已占用） |
| **PA_20（24 脚）** | **选用**：固件零引用；板上默认功能为震动马达 PWM |

**⚠️ 马达注意事项**（LCKFB wiki 原文）：PA20 默认为 VIB PWM，"扩展时核心板上的马达不能焊接"。已写入 `sifli_ap.c` 代码注释。

### 2.2 实现

- **defconfig**：`CONFIG_SENSORS_DHTXX=y`（contest 仓硬链接同步）。
- **板级**（`sifli_ap.c`）：PA20 → `GPIO_A20`（内部上拉），NuttX 树内 `dhtxx` 驱动注册为 `/dev/dhtxx0`，类型 `DHTXX_DHT22`（16 位 ×0.1 格式、负温符号位由驱动解析）。GPIO 回调按 `GPIO_InitTypeDef{Pin=编号, Mode, Pull}` 实现；微秒时钟用 **Cortex-M33 DWT 循环计数器**（`HAL_DBG_DWT_GetCycles`，与 `HAL_Delay_us` 同源，本平台已验证可用），累加器方案保证 32 位 CYCCNT 回绕安全。
- **应用端修复**：原温湿度页面按文本 `"temp hum"` 解析（`fgets`+`sscanf`），而 dhtxx 驱动 `read()` 返回**二进制** `struct dhtxx_sensor_data_s {float hum; float temp; status}`——原实现即使驱动正常也会恒报 Read error。已改为结构体读取；瞬时校验失败保留上次读数，仅首次失败显示 Read error。
- **BLE 上传**：复用 `ai_watch_ble_send_sensor_data()`，DataUpload(f3) 通道 notify `[version(1)][type(1)][payload]`：温度 `AI_WATCH_BLE_SENSOR_TEMP=0x01`、湿度 `=0x02`，均为 float32 LE。手机端订阅 f3 即可。
- 采样周期 2s（驱动强制，`DHT_UPDATE_MS=2000`）；定时器随页面创建/销毁，打开页面才有阻塞读（单次约 25ms）。

### 2.3 与 DHT11 例程的差异（用户参考其 STM32 工程时注意）

- 数据格式：DHT11 整数字节；DHT22 为 16 位 ×0.1（湿度 16 位、温度 16 位含符号位、校验和）。
- 引脚排布：DHT22 面向网格面从左到右 **VCC、DATA、NC（悬空）、GND**，第 3 脚是空脚，勿按 DHT11 接法。
- 时钟：板上无 `Delay_us` 精确忙等，用 DWT 计数器换算微秒。
